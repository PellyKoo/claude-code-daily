## 1. 路径作用域规则：用 .claude/rules/ 替代巨型 CLAUDE.md
- **来源**: [Towards AI](https://pub.towardsai.net/claude-md-best-practices-13cfe020050d) on Medium | 🔥 高互动技术文章
- **摘要**: 与其把所有规则塞进一个 CLAUDE.md，不如按目录拆分到 `.claude/rules/` 下。例如 `src/api/` 相关的 API 约定放在路径作用域文件中，Claude 只在处理该目录文件时才会加载这些规则。每个规则文件保持在 200 行以内。这样既减少上下文噪音，又让规则更精准。
- **代码示例**:
```
.claude/
├── rules/
│   ├── api-conventions.md      # 仅在处理 src/api/ 时加载
│   ├── test-patterns.md        # 仅在处理测试文件时加载
│   └── database-migrations.md  # 仅在处理迁移文件时加载
└── CLAUDE.md                   # 全局规则，保持简短
```

## 2. Stop Hook：让 Claude 每轮结束时自动验证产出
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 600+ stars 社区最佳实践合集
- **摘要**: 在 `.claude/settings.json` 中配置 Stop hook，让 Claude 在每次停下来之前自动运行验证脚本（如 lint、typecheck、test）。这样不需要手动提醒 Claude "记得跑测试"，每轮结束都会自动检查。搭配 PostToolUse hook（Write/Edit 后自动格式化）形成完整的质量保障闭环。
- **代码示例**:
```json
{
  "hooks": {
    "Stop": [{
      "command": "npm run typecheck && npm run lint -- --quiet",
      "description": "每轮结束自动验证类型和规范"
    }],
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "command": "npx prettier --write $CLAUDE_FILE_PATH"
    }]
  }
}
```

## 3. 团队 Makefile 集成：用 Headless 模式标准化 AI 工作流
- **来源**: [Collabnix](https://collabnix.com/claude-code-best-practices-10-workflow-tips-that-senior-engineers-swear-by-in-2026/) on Blog | 🔥 资深工程师实践分享
- **摘要**: 高级工程师推荐将 Claude Code 的 headless 模式（`claude -p`）封装到团队 Makefile 中。通过 `--allowedTools` 限制可用工具、`--max-turns` 控制轮次上限，团队成员可以用统一命令做代码审查、生成测试、更新文档等。避免每个人用不同的 prompt 得到参差不齐的结果，同时严格控制 API 成本。
- **代码示例**:
```makefile
# Makefile
review:
	claude -p "Review changed files for bugs and security issues" \
		--allowedTools "Read,Grep,Glob" \
		--max-turns 5 \
		--output json

gen-tests:
	claude -p "Generate unit tests for files changed in this branch" \
		--allowedTools "Read,Write,Grep,Glob,Bash" \
		--max-turns 10

update-docs:
	claude -p "Update README and API docs based on recent code changes" \
		--allowedTools "Read,Write,Glob" \
		--max-turns 8
```

## 4. 从振动编码到代理工程：系统化 Claude Code 实践
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 600+ stars
- **摘要**: 这个 GitHub 仓库系统性地整理了从"振动编码"（vibe coding，随意使用 AI）进阶到"代理工程"（agentic engineering，系统化使用 AI）的完整实践。核心理念：把 Claude 当成一个需要 onboarding 的新团队成员，而不是一个搜索引擎。提供了 CLAUDE.md 编写、Git 工作流、多代理协作、CI/CD 集成等维度的结构化指南。
- **代码示例**:
```markdown
<!-- CLAUDE.md 中的 onboarding 模式 -->
## 项目概述
这是一个 [技术栈] 项目，用于 [核心功能]。

## 开发流程
1. 修改前先阅读相关模块的测试文件
2. 每个逻辑单元单独提交，使用 conventional commits
3. 提交前确保 `make check` 通过

## 常见陷阱
- 不要修改 generated/ 目录下的文件
- 数据库迁移必须是可回滚的
```

## 5. Claude Code 生产力工作流大全：8 种场景实战

## 6. CLAUDE.md 简洁之道：每条规则必须通过"删除测试"
- **来源**: [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md) on Blog | 🔥 专题深度文章
- **摘要**: 编写 CLAUDE.md 的核心原则是"删除测试"——对每一条规则问自己：如果删掉这条，Claude 会犯错吗？如果答案是否，就删掉它。避免在 CLAUDE.md 中放代码片段（容易过期），改用 `file:line` 引用。不要写"不要做 X"这种否定句式，改为正面描述期望行为。全局文件控制在 200 行以内。
- **代码示例**:
```markdown
<!-- ❌ 冗余规则（Claude 本身就会这样做） -->
- 使用有意义的变量名
- 保持函数短小

<!-- ❌ 容易过期的代码片段 -->
认证使用如下模式：
```typescript
const auth = new AuthClient({...})
```

<!-- ✅ 精准的、Claude 不知道的项目特定规则 -->
- 数据库查询用 src/db/queries.ts 中的预定义查询，不要写内联 SQL
- CI 中 `npm test` 最长运行 3 分钟，超时则拆分测试文件
```

## 7. 15 条来自 6 个真实项目的实战经验
- **来源**: [AI Org](https://aiorg.dev/blog/claude-code-best-practices) on Blog | 🔥 多项目实践总结
- **摘要**: 从 6 个不同规模的真实项目中提炼出 15 条 Claude Code 最佳实践。几个亮点：用 `git diff` 作为 Claude 的"工作范围提示"比口头描述更精准；在 CLAUDE.md 中列出"禁止自动修改的文件列表"防止 Claude 误改配置文件；为每种 PR 类型（feature、bugfix、refactor）定义不同的检查清单让 Claude 对照执行。
- **代码示例**:
```markdown
<!-- CLAUDE.md 中定义不同 PR 类型的检查清单 -->
## PR 检查清单

### Feature PR
- [ ] 有对应的测试覆盖
- [ ] 更新了 API 文档
- [ ] 添加了 migration（如需要）

### Bugfix PR
- [ ] 有复现 bug 的回归测试
- [ ] 在 commit message 中引用了 issue 号

## 禁止自动修改的文件
- .env.example
- docker-compose.yml
- infrastructure/
```
