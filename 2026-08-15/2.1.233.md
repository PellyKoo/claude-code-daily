## 1. Skill 审计法：一键清理冗余 Skills
- **来源**: [Prajwal Tomar](https://x.com/PrajwalTomar_/status/2074787074641899896) on X | 🔥 高互动推文
- **摘要**: 把 Claude Code 技巧文章全文粘贴进会话，然后让 Claude 自动对比已安装的 Skills 列表与文章推荐列表——卸载重叠的、从未触发的、以及被更好替代的 Skill，最后输出"优化前后的上下文占用对比"。这个方法能显著减少 CLAUDE.md 膨胀和上下文浪费。
- **代码示例**:
```
# 将技巧文章粘贴进会话后输入：
"Read this article end to end. Then list every skill 
I currently have installed, and compare it against this list. 
Uninstall anything that overlaps, never triggers, or is a 
worse version. Give me a before/after context count."

# 效果：
# - 清理从未触发的僵尸 Skill
# - 合并功能重叠的 Skill
# - 减少每次会话的上下文消耗
```

## 2. 上下文 30% 铁律：别让 Claude 变笨
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.6k stars, 6.4k forks
- **摘要**: 这个拥有 6.4 万 Star 的社区最佳实践仓库提出了比之前 70% 更激进的观点："笨区"在约 40% 上下文时就开始了，应该积极将上下文保持在 30% 以下。切换任务时立即 `/compact` 或 `/clear`。另一个关键发现：使用 `rewind > correct` 策略——双击 Esc 回退到失败尝试之前，而不是在上下文中堆积修正指令，因为失败的尝试会污染上下文质量。
- **代码示例**:
```bash
# 上下文健康管理（更激进的策略）
# 30% 以下：安全区，正常工作
# 30-40%：警戒区，考虑 /compact
# 40%+："笨区"，立即 /compact 或 /clear

# 切换任务时的标准流程：
/compact     # 或 /clear（如果任务完全不同）

# Rewind > Correct 原则：
# ❌ 错误做法：Claude 搞错了 → 告诉它"不对，应该这样..."
# ✅ 正确做法：Claude 搞错了 → Esc+Esc 回退 → 重新给更精确的指令
# 原因：修正指令会留在上下文中，污染后续推理
```

## 3. context: fork 隔离术：让 Skill 在独立沙箱运行
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.6k stars, 6.4k forks
- **摘要**: 在 Skill 定义中使用 `context: fork` 参数，可以让 Skill 在独立的子 Agent 上下文中运行——主上下文只看到最终结果，看不到中间的工具调用和探索过程。这对于复杂的代码审查、搜索、分析类 Skill 尤其有价值，因为这些操作往往产生大量中间输出，会严重消耗主上下文容量。
- **代码示例**:
```yaml
# .claude/skills/deep-review.md 示例
---
name: deep-review
context: fork    # 关键：在独立子 Agent 中运行
description: 深度代码审查
---

# 审查步骤
1. 读取所有变更文件
2. 检查安全漏洞
3. 检查性能问题
4. 输出结构化报告

# 效果对比：
# 无 fork：审查过程占用主上下文 ~50k tokens
# 有 fork：主上下文只接收最终报告 ~2k tokens
```

## 4. Settings 权限精细化：复合命令自动拆分验证
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice/blob/main/best-practice/claude-settings.md) on GitHub | ⭐ 64.6k stars
- **摘要**: 社区发现一个容易踩的坑：`Bash(safe-cmd *)` 的权限规则并不会授权 `safe-cmd && other-cmd` 这样的复合命令——Claude Code 会自动拆分复合 shell 命令，每个部分独立匹配权限规则。另外，`timeout`、`time`、`nice` 等进程包装器会被自动剥离后再匹配，而 `watch`、`setsid` 等 exec 包装器则始终需要提示确认。掌握这些规则可以写出既安全又不频繁弹权限提示的配置。
- **代码示例**:
```json
// .claude/settings.json - 安全且低打扰的权限配置
{
  "permissions": {
    "allow": [
      "Edit(src/**)",
      "Read(.env)",
      "Bash(npm run *)",
      "Bash(npx vitest *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "deny": [
      "Bash(rm -rf /)",
      "Read(./secrets/**)"
    ]
  }
}

// 注意事项：
// ✅ Bash(npm run test)     → 匹配 "npm run *"
// ❌ Bash(npm run test && rm -rf .) → 拆分验证，rm 被拒绝
// ✅ Bash(timeout 30 npm test)  → timeout 被剥离，匹配 "npm *"
// ❌ Bash(watch npm test)    → watch 始终需要确认
```

## 6. Sandbox + 凭证保护：安全的自动化开发环境
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice/blob/main/best-practice/claude-settings.md) on GitHub | ⭐ 64.6k stars
- **摘要**: 社区推荐的安全实践：启用沙箱模式后配合凭证保护，可以让 Claude 自由执行 bash 命令而不用担心泄露敏感信息。通过 `credentials.files` 遮蔽本地凭证文件（如 AWS credentials），通过 `credentials.envVars` 阻止敏感环境变量（如 GITHUB_TOKEN）被读取。结合 `network.allowedDomains` 白名单，构建一个既高效又安全的自动化开发环境。
- **代码示例**:
```json
// settings.json - 沙箱 + 凭证保护配置
{
  "sandbox": {
    "enabled": true,
    "autoAllowBashIfSandboxed": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "mask" },
        { "path": "~/.ssh/id_rsa", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "AWS_SECRET_ACCESS_KEY", "mode": "deny" }
      ]
    },
    "network": {
      "allowedDomains": [
        "api.github.com",
        "registry.npmjs.org"
      ],
      "strictAllowlist": true
    }
  }
}

// 效果：
// ✅ Claude 可以自由运行 npm/git 命令
// ✅ 网络请求被限制在白名单域名
// ❌ 无法读取 AWS 凭证和 SSH 密钥
// ❌ 无法访问 GITHUB_TOKEN 环境变量
```

## 7. 原型优先策略：用 20 次迭代替代写 PRD
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.6k stars, 6.4k forks
- **摘要**: 社区总结的颠覆性工作流理念：`prototype > PRD`（原型优先于产品需求文档）。核心论点是 AI 编码的成本已经足够低，与其花时间写详细的 PRD 然后一次性实现，不如快速构建 20-30 个原型版本，通过实际迭代收敛到最优方案。配合垂直切片开发（Tracer Bullet 跨所有层走通一条路径）而非传统的水平分层开发。这个策略在社区引起了激烈讨论。
- **代码示例**:
```bash
# 原型优先工作流（vs 传统 PRD 工作流）

# ❌ 传统方式：
# 1. 写 PRD（2-4小时）
# 2. 设计架构（1-2小时）
# 3. 实现（4-8小时）
# 4. 发现需求不对，返工

# ✅ 原型优先方式：
# 1. 给 Claude 一句话描述 → 10分钟出原型
# 2. 评估 → 调整方向 → 再出原型
# 3. 重复 20-30 次（每次 ~10分钟）
# 4. 从最佳原型中提炼出生产代码

# 垂直切片开发（Tracer Bullet）：
"实现用户注册功能的完整垂直切片：
从前端表单 → API endpoint → 数据库写入 → 返回响应。
先跑通最简路径，不要做水平分层。"

# 而不是：
# "先设计所有 API → 再写所有数据库 → 最后做前端"
```

## 8. Managed Settings 与团队策略统一管理
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice/blob/main/best-practice/claude-settings.md) on GitHub | ⭐ 64.6k stars
- **摘要**: 针对团队场景的高级配置技巧：使用 `managed-settings.d/` 目录（类似 systemd 的 drop-in 机制）管理团队策略，文件按字母序合并，后者覆盖前者。配合 `requiredMinimumVersion` / `requiredMaximumVersion` 锁定 CLI 版本范围、`policyHelper` 动态计算管理策略、以及 `env` 字段注入环境变量（不需要 wrapper 脚本），可以实现企业级的 Claude Code 统一管理。
- **代码示例**:
```json
// managed-settings.d/01-base.json - 基础策略
{
  "requiredMinimumVersion": "2.1.200",
  "requiredMaximumVersion": "2.2.0",
  "enforceAvailableModels": true,
  "env": {
    "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "500000"
  }
}

// managed-settings.d/02-security.json - 安全策略
{
  "permissions": {
    "deny": ["Bash(curl *)", "Bash(wget *)"],
    "allow": ["Bash(npm run *)"]
  },
  "sandbox": { "enabled": true },
  "allowManagedHooksOnly": true
}

// managed-settings.d/03-team-hooks.json - 团队 Hooks
{
  "hooks": {
    "pre-commit": "npm run lint && npm run typecheck"
  },
  "disableAllHooks": false
}

// 效果：文件按 01 → 02 → 03 顺序合并
// 团队成员无需手动配置，统一策略自动生效
```
