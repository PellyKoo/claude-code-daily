## 1. 动态 Workflow 的四种启动方式
- **来源**: [Daniel San (@dani_avila7)](https://x.com/dani_avila7/status/2082282569718980637) on X | 🔥 高互动讨论帖
- **摘要**: Claude Code 的 Workflow 编排能力可以通过四种方式触发：`/deep-research <question>` 启动深度研究工作流；在 prompt 中加入 `ultracode:` 前缀触发全面多代理编排；用自然语言说"use a workflow"让 Claude 自动生成脚本；或用 `/effort ultracode` 让 Claude 在整个会话中自行决定何时启用工作流。社区反馈：大多数人不知道可以用自然语言直接触发 workflow，这是最容易被忽略的入口。
- **代码示例**:
```bash
# 方式 1: 深度研究
/deep-research 这个项目的性能瓶颈在哪里？

# 方式 2: ultracode 前缀（最彻底）
ultracode: 重构这个模块的错误处理逻辑

# 方式 3: 自然语言触发
"帮我审查这个 PR，use a workflow 并行检查 bug、性能和安全性"

# 方式 4: 会话级别设置
/effort ultracode
# 之后的所有复杂任务，Claude 自动判断是否需要 workflow
```

## 2. 按需加载规则：.claude/rules/ 目录的妙用
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.1k stars, 6.4k forks
- **摘要**: 与其把所有规则塞进一个 CLAUDE.md，不如使用 `.claude/rules/*.md` 按领域拆分，并通过 YAML frontmatter 的 `paths:` 字段实现按需加载——只有当 Claude 操作到相关文件时，对应的规则才会被注入上下文。这解决了 CLAUDE.md 过长导致重要指令被"淹没"的痛点。社区数据：规则文件控制在 200 行以内时，Claude 的遵循度最高。
- **代码示例**:
```markdown
<!-- .claude/rules/database.md -->
---
paths:
  - "src/db/**"
  - "prisma/**"
  - "*.prisma"
---

- 所有数据库迁移必须是可逆的（包含 up 和 down）
- 新增字段必须设置默认值，避免锁表
- 查询必须使用参数化，禁止字符串拼接

<!-- .claude/rules/api.md -->
---
paths:
  - "src/api/**"
  - "src/routes/**"
---

- 所有端点必须有输入验证（使用 zod）
- 错误响应遵循 RFC 7807 格式
- 分页接口使用 cursor-based pagination
```

## 3. Plan Mode：先审后改的安全工作流
- **来源**: [Claude Code Workflow Best Practices](https://dev.to/galian/claude-code-workflow-best-practices-that-ship-code-na) on DEV.to | 🔥 热门技术博文 & 社区最佳实践
- **摘要**: 启动 Claude Code 时使用 `claude --permission-mode plan` 进入只读模式，Claude 只能读取文件和分析代码，不能做任何修改。这是处理大型功能和陌生代码库的最安全起点。社区推荐的"阶梯式"工作流：先 plan mode 理解代码 → 确认方案 → 切换到正常模式执行 → 每完成一步说"做完第 N 步，停下来给我看"。这种方式将错误捕获从第六步提前到第一步。
- **代码示例**:
```bash
# Step 1: 以只读模式启动，先理解再动手
claude --permission-mode plan

# Step 2: 在 plan mode 中让 Claude 分析
"分析这个支付模块的架构，列出所有依赖关系
和潜在的重构风险点。不要修改任何代码。"

# Step 3: 确认方案后切换到执行模式
# 退出 plan mode，重新启动正常模式

# Step 4: 阶梯式执行
"按照刚才的方案，先做第一步：
提取公共接口。做完停下来给我看。"

# Step 5: 审查后继续
"第一步看起来没问题。继续第二步。"
```

## 4. /compact 手动压缩：上下文管理的关键技巧
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.1k stars & 多个社区经验帖
- **摘要**: Claude Code 会在接近上下文窗口极限时自动压缩对话，但社区发现主动管理效果更好。最佳实践是在上下文使用到约 50% 时手动执行 `/compact`，这样可以保留更多关键信息的同时释放空间。特别适合长会话和复杂重构场景。另一个技巧：在 compact 前先给 Claude 一句"请在压缩时保留 X、Y、Z 的决策理由"，可以定向保留关键上下文。
- **代码示例**:
```bash
# 查看当前上下文使用量
# Claude Code 界面底部会显示 token 使用比例

# 在 50% 左右时主动压缩
/compact

# 带指引的压缩（保留关键上下文）
/compact 请保留：1) 数据库 schema 变更的决策理由
2) API 接口的兼容性约束 3) 已完成的步骤清单

# 长会话策略：
# 1. 每完成一个大的子任务后 /compact
# 2. 切换到新文件/模块前 /compact
# 3. 遇到 Claude "忘记"之前讨论的内容时 /compact
```

## 5. GitHub Actions 自动化：CI 级别的 Claude 集成
- **来源**: [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 6k stars, 565 forks
- **摘要**: showcase 仓库展示了四个生产级的 GitHub Actions 工作流，将 Claude Code 嵌入 CI/CD 流程：每个 PR 自动代码审查（单次约 $0.05-$0.50）、每周代码质量巡检（约 $1-$5）、每月文档同步（约 $0.50-$2）、每两周依赖审计（约 $0.20-$1）。社区估算完整配置的月成本在 $10-$50，显著低于人工审查成本。关键优势：审查标准完全一致，不会因审查者不同而标准波动。
- **代码示例**:
```yaml
# .github/workflows/claude-pr-review.yml
name: Claude Code PR Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Claude Code Review
        uses: anthropics/claude-code-action@v1
        with:
          prompt: |
            Review this PR for:
            1. Bug risks and edge cases
            2. Performance concerns
            3. Security vulnerabilities
            4. Code style consistency
          model: claude-sonnet-5
          # 成本控制：使用 Sonnet 而非 Opus
          # 每次审查约 $0.05-$0.50
```

## 6. /rewind + 摘要：会话状态的精确回溯
- **来源**: [Santiago (@svpino)](https://x.com/svpino/status/2050563493708112190) on X | 🔥 20条技巧合集，高互动
- **摘要**: `/rewind` 不只是简单的撤销——它是会话状态管理的核心工具。Santiago 分享的高级用法：回退到某个检查点后，不是重做，而是让 Claude 从该点开始"总结到这里为止的所有内容"。这会产生一个精炼的上下文摘要，既释放了 token 空间，又保留了关键决策。社区称之为"手动 checkpoint + compact 组合拳"，特别适合探索性开发——先大胆尝试，不满意就 rewind，满意就 summarize 后继续。
- **代码示例**:
```bash
# 基础用法：回退到检查点
/rewind
# → 显示检查点列表，选择回退目标

# 高级用法：回退 + 摘要（Santiago 的技巧）
/rewind
# 选择一个较早的检查点
"Summarize from here"
# → Claude 总结从该检查点到现在的所有工作
# → 上下文被压缩，但关键信息保留

# 探索性开发流程：
# 1. 让 Claude 尝试方案 A
# 2. 不满意 → /rewind 回到尝试前
# 3. 让 Claude 尝试方案 B
# 4. 满意 → "Summarize from here" 锁定进度
# 5. 继续下一个任务

# 配合 Esc+Esc 使用：
# Esc+Esc 是快速回退（UI 交互）
# /rewind 是精确回退（可选检查点 + 摘要）
```

## 7. 验证循环：让 Claude 自己检查输出
- **来源**: [Claude Code Hacks 2026](https://youmind.com/landing/x-viral-articles/claude-code-hacks-2026-workflow) & 多个社区最佳实践帖 | 🔥 社区公认最有价值的单一技巧
- **摘要**: 社区一致认为，如果只能采纳一个 Claude Code 技巧，那就是"验证循环"——在 prompt 中明确要求 Claude 检查自己的输出。具体做法：在 CLAUDE.md 或 prompt 中加入验证指令，如"写完代码后运行测试"、"修改后用 TypeScript 编译器检查类型"、"实现后打开浏览器验证渲染结果"。让 Claude 有一个可执行的验证手段，而不是靠自我审查（self-review 准确率远低于工具验证）。
- **代码示例**:
```markdown
<!-- 在 CLAUDE.md 中添加验证规则 -->

## 验证要求
- 修改代码后，必须运行 `npm test` 确认没有破坏现有测试
- 添加新功能后，必须编写对应的测试用例并运行通过
- 修改 TypeScript 代码后，运行 `npx tsc --noEmit` 检查类型
- 修改 UI 组件后，启动 dev server 并截图验证渲染结果
- 修改 API 后，用 curl 发送测试请求并验证响应格式
```

```bash
# 在 prompt 中嵌入验证步骤
"重构 UserService 的错误处理。完成后：
1. 运行 npm test 确保所有测试通过
2. 运行 tsc --noEmit 确保类型安全
3. 如果有失败，自动修复后重新验证"
```

## 8. 子代理的正确打开方式：渐进式任务分解
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.1k stars & [35+ Claude Code Tips](https://x.com/Suryanshti777/status/2029200211093201017) on X
- **摘要**: 社区总结了子代理（subagents）的使用心得：不要泛泛地使用"use subagents"，而是采用"渐进式披露"模式——为特定功能创建预加载了相关 skills 的专用子代理，而非通用型子代理。另一个关键点：子代理不能通过 bash 命令调用其他子代理，必须使用 `Agent()` API。社区经验是每个子代理聚焦单一任务（如"专门审查 SQL 注入风险"），比一个子代理做多件事效果好得多。
- **代码示例**:
```bash
# ❌ 模糊的子代理请求
"use subagents 来审查这个 PR"

# ✅ 明确的任务分解
"审查这个 PR，为以下维度各启动一个子代理：
1. SQL 注入和 XSS 安全风险
2. N+1 查询和内存泄漏性能问题
3. 错误处理的完整性和一致性"

# 在 prompt 中请求子代理时的最佳模式
"搜索这个代码库中所有使用 eval() 的地方。
这个任务适合用子代理并行搜索不同目录。"

# 关键限制：子代理之间不能嵌套调用
# Agent A 不能在内部启动 Agent B
# 需要嵌套时使用 Workflow 替代
```
