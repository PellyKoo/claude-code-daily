# Claude Code 2.1.211 社区实用技巧 - 2026-07-15

## 1. AskUserQuestionTool 面试法：让 Claude 主动追问需求细节
- **来源**: [Filip Kowalski](https://x.com/filippkowalski/status/2010317972774994085) on X | 🔥 高互动热帖
- **摘要**: 在提交功能需求时，末尾追加一段指令要求 Claude 通过 AskUserQuestionTool 对你进行"深度访谈"，覆盖技术细节、边界情况和业务约束。Claude 会连续提出 5-15 个针对性问题，帮你发现自己都没考虑到的需求盲区。访谈结束后，开启新会话把完善后的 spec 交给 Claude 执行——因为新会话的上下文窗口是干净的，执行质量显著更高。
- **代码示例**:
```markdown
# 在你的功能需求末尾追加：
"interview me in detail using the AskUserQuestionTool about
literally anything: technical decisions, edge cases, error
handling, UX flows, data models, performance requirements.
Ask one question at a time. Don't stop until you've covered
every ambiguity."

# 访谈结束后：
1. 把 Claude 整理好的完整 spec 复制出来
2. /clear 或开启新会话
3. 把 spec 粘贴进去让 Claude 执行
```

## 2. Skills 即斜杠命令：把复杂提示词打包成一键操作
- **来源**: [Ruben Hassid](https://x.com/rubenhassid/status/2071911634403053890) on X | 🔥 高互动热帖
- **摘要**: Claude Code 的 Skill 系统本质上是"可复用的长提示词"，放进 `.claude/skills/` 目录后就变成了斜杠命令。不需要写代码，只需要把你平时反复输入的复杂提示整理成 markdown 文件。比如代码审查清单、部署流程、重构模式等，每个 skill 可以包含完整的指令链、约束条件和输出格式。团队成员只需 `/skill-name` 即可调用，消除了"每个人提示方式不一样导致结果不一样"的问题。
- **代码示例**:
```markdown
<!-- .claude/skills/security-audit.md -->
---
description: "Run a security audit on changed files"
---

Review all changed files for security vulnerabilities:
1. Check for SQL injection, XSS, CSRF
2. Verify input validation at all boundaries
3. Check for hardcoded secrets or credentials
4. Review authentication and authorization logic
5. Output findings as a table: severity | file | line | issue | fix

<!-- 使用方式：直接输入 /security-audit -->
```

## 3. 修复 Claude 偷懒：调整系统提示中的"简洁 vs 详尽"比例
- **来源**: [Elie Steinbock](https://x.com/elie2222/status/2041477770245451885) on X | 🔥 高互动热帖
- **摘要**: Claude Code 的系统提示中有约 20 处指令要求"保持简洁"，但只有 4 处鼓励"详尽"——5:1 的比例天然倾向偷工减料。解决方案是在项目级 CLAUDE.md 中明确要求完整实现：不跳过边界情况、不用占位符、不省略错误处理。这不是在"破解"系统，而是用项目指令来平衡默认行为，让 Claude 的输出符合生产代码标准。
- **代码示例**:
```markdown
<!-- CLAUDE.md 中添加以下规则 -->

## Code Quality Rules
- NEVER use placeholder comments like "// ... rest of implementation"
- NEVER skip error handling or edge cases
- ALWAYS implement complete functions, not stubs
- When modifying a file, preserve ALL existing functionality
- If a function has 10 cases, implement all 10, not just the "common" ones
- Write production-ready code, not demo code
```

## 4. 自定义状态栏：实时掌控会话关键指标
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.3k stars
- **摘要**: Claude Code 底部的状态栏可以完全自定义，实时显示当前模型、Git 分支、未提交文件数、token 用量、上下文压缩次数等关键信息。通过 shell 脚本动态生成状态内容，你不再需要反复输入 `/usage` 或 `git status` 来了解会话状态。这个看似微小的改动实际上从根本上改变了你与 Claude Code 的交互方式——从"被动猜测"变成"主动监控"。
- **代码示例**:
```json
// settings.json 中配置自定义状态栏
{
  "statusLine": {
    "script": "~/.claude/scripts/status.sh"
  }
}
```
```bash
#!/bin/bash
# ~/.claude/scripts/status.sh
BRANCH=$(git branch --show-current 2>/dev/null || echo "no-repo")
DIRTY=$(git status --porcelain 2>/dev/null | wc -l | tr -d ' ')
echo "🌿 $BRANCH | 📝 ${DIRTY} changed"
```

## 5. 跨模型审查：用第二个 Claude 实例当"首席工程师"
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 62.9k stars
- **摘要**: 在同一个项目目录中开启两个 Claude Code 实例，一个负责编码，另一个充当"Staff Engineer"角色专门审查前者的产出。第二个实例拥有独立的上下文窗口，不受编码过程中的思维惯性影响，因此更容易发现架构层面的问题。这种"测试时计算"（test-time compute）模式利用了一个核心洞察：分离的上下文窗口天然产生多样化的视角。
- **代码示例**:
```bash
# 终端 1：编码实例
cd my-project && claude
> 实现用户认证模块，使用 JWT + refresh token

# 终端 2：审查实例（同一目录，独立上下文）
cd my-project && claude
> 你是一位经验丰富的 Staff Engineer。
  请审查当前项目中最近修改的文件，重点关注：
  1. 安全漏洞（token 存储、密钥管理）
  2. 架构合理性（职责分离、依赖方向）
  3. 边界情况处理（并发、过期、撤销）
  给出具体的改进建议和代码修改方案。
```

## 6. /compact 带提示词：智能压缩而非盲目截断
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 62.9k stars
- **摘要**: 大多数人用 `/compact` 时不加任何参数，让 Claude 自己决定保留什么。但你可以在 `/compact` 后面附加提示词，告诉 Claude 压缩时应该重点保留哪些信息。比如 `/compact keep all architecture decisions and API contracts` 会确保架构决策不在压缩中丢失。这比自动压缩的效果好得多，因为你比 Claude 更清楚当前任务的核心上下文是什么。
- **代码示例**:
```bash
# ❌ 不推荐：无参数压缩
> /compact
# Claude 可能丢弃你认为重要的决策上下文

# ✅ 推荐：带提示词的定向压缩
> /compact retain all database schema decisions, API endpoint
  signatures, and the error handling pattern we established

# ✅ 推荐：面向特定任务的压缩
> /compact I'm about to start the payment integration,
  keep everything related to the order model and pricing logic

# ✅ 推荐：多轮对话后重新聚焦
> /compact summarize what we built, drop all debugging context,
  keep the final working implementation details
```

## 7. Skill 描述写成触发条件而非功能摘要
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 62.9k stars
- **摘要**: 定义 Skill 时，`description` 字段决定了 Claude 何时自动推荐该 skill。如果你写"数据库迁移工具"，Claude 只在用户明确提到"迁移"时才触发。但如果你写成触发条件——"当用户修改 schema 文件、添加新的数据模型、或提到数据库变更时使用"——Claude 会在更多相关场景中主动推荐，大幅提升 skill 的使用频率和实际价值。
- **代码示例**:
```markdown
<!-- ❌ 不推荐：功能摘要式描述 -->
---
description: "Database migration helper"
---

<!-- ✅ 推荐：触发条件式描述 -->
---
description: "Use when the user modifies a schema file,
adds a new data model, mentions database changes, renames
a column, or asks about data migration. Also trigger when
files matching *.schema.ts or migrations/* are edited."
---

<!-- ❌ 不推荐 -->
---
description: "Code review checklist"
---

<!-- ✅ 推荐 -->
---
description: "Use before any git commit, when the user says
'review', 'check my code', 'ready to commit', or when
changes span more than 3 files."
---
```

## 8. 语音输入：用说话代替打字与 Claude 交互
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.3k stars
- **摘要**: 使用本地语音转录工具（如 SuperWhisper、MacWhisper 或系统自带的语音输入）直接对 Claude Code 说话，比打字快 3-5 倍。特别适合描述复杂需求、解释业务逻辑、或进行头脑风暴式的对话。语音输入的"啰嗦"恰好是优势——Claude 从自然语言中提取意图的能力极强，更多的上下文描述反而能得到更精准的结果。配合 AskUserQuestionTool 面试法效果更佳。
- **代码示例**:
```bash
# macOS：使用系统自带语音输入
# 按两下 Fn 键激活听写，对着麦克风说需求

# SuperWhisper（推荐）：本地运行 Whisper 模型
# 安装后设置全局快捷键，转录结果自动粘贴到当前焦点窗口
# 支持中英文混合识别

# Linux：使用 nerd-dictation + Whisper
pip install openai-whisper
# 配置快捷键绑定到语音转录脚本
```
