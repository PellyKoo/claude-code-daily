# Claude Code 2.1.314 社区实用技巧 - 2026-10-30

## 1. Mods 系统：自定义 Claude Code 的行为和界面
- **来源**: [AGTP (@AGTPinsights)](https://x.com/AGTPinsights/status/2105768033419743253) on X | 🔥 高互动讨论
- **摘要**: Claude Code 在 10 月初推出了 Mods 功能，允许开发者自定义 Claude Code 的行为和外观。你可以通过 `/plugin` 安装社区制作的 mod，修改面板布局、添加状态栏组件、自定义 slash 命令，甚至为工具调用添加钩子。这让 Claude Code 从一个固定工具变成了一个可扩展平台，社区已经开始涌现各种实用插件。
- **代码示例**:
```bash
# 安装社区 mod
/plugin install <mod-name>

# Mods 可以做的事情：
# - 添加自定义面板 (pane) 到聊天侧边
# - 修改状态栏显示内容
# - 添加新的 slash 命令
# - 在工具调用前后触发自定义逻辑 (hooks)
```

## 2. Dynamic Workflows：让 Opus 编排，廉价模型执行
- **来源**: [delost (@thedelost)](https://x.com/thedelost/status/2110472847084650726) on X | 🔥 高赞分享
- **摘要**: 社区开发者发现了一个高效工作模式：让 Opus 5.5 编写工作流脚本作为"计划"，然后由一群更便宜的子 Agent 执行具体任务。这样做的好处是 Opus 只负责架构级思考，不会被大量代码细节消耗 token。适合大规模重构、批量代码审查等场景。有用户报告在处理大型项目时 token 消耗降低了 60% 以上。
- **代码示例**:
```javascript
// 在提示词中加入 "workflow" 或开启 ultracode 模式
// Claude 会自动生成编排脚本，例如：
export const meta = {
  name: 'batch-refactor',
  description: 'Refactor all API handlers',
  phases: [{ title: 'Scan' }, { title: 'Refactor' }, { title: 'Verify' }],
}
// Opus 写脚本 → 子 Agent 按脚本执行 → 自动验证结果
```

## 3. CLAUDE.md 精简法则：控制在 200 行以内
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 高星仓库
- **摘要**: 多个社区指南一致建议：CLAUDE.md 文件应控制在 200 行以内。过长的配置文件不仅消耗宝贵的上下文窗口，还会降低 Claude 对规则的遵守率。核心策略：只写 Claude 无法从代码中推断出的规则；把可变规则拆分到 `.claude/rules/` 下按路径作用域加载；强制行为（如权限、归因）放 settings.json 而非靠 CLAUDE.md 描述。
- **代码示例**:
```markdown
# 精简 CLAUDE.md 的三个原则：

# 1. 规则要可检查，不要模糊
# ❌ "格式化代码"
# ✅ "运行 npm run lint 后再提交"

# 2. 删除 Claude 能推断的内容
# ❌ "本项目使用 TypeScript"（Claude 看文件就知道）
# ✅ "API 响应必须包含 request_id 字段"（隐含约束）

# 3. 大型项目用路径作用域
# .claude/rules/api.md → 只在编辑 src/api/ 时加载
# .claude/rules/tests.md → 只在编辑 tests/ 时加载
```

## 4. Git Worktrees 实现多会话并行开发
- **来源**: [PrajwalTomar_ 的 Claude Code Playbook](https://x.com/PrajwalTomar_/article/2063238968125333581) on X | 🔥 长文高赞
- **摘要**: 使用 git worktrees 可以让多个 Claude Code 会话同时工作在不同分支上，互不干扰。推荐从 2 个并行会话开始，熟练后再增加。每个 worktree 是完全独立的工作目录，一个 Agent 做功能开发，另一个同时做测试编写，效率翻倍。Claude Code 原生支持 `--worktree` 参数直接创建工作树。
- **代码示例**:
```bash
# 方法一：使用 Claude Code 内置命令
claude --worktree feature-auth
claude --worktree fix-api-bug

# 方法二：手动创建 worktree
git worktree add ../feature-auth -b feature-auth
cd ../feature-auth && claude

# 并行场景示例：
# 终端 1：claude --worktree feature-login  → 开发登录功能
# 终端 2：claude --worktree test-suite     → 编写测试用例
# 终端 3：claude --worktree refactor-db    → 重构数据库层
```

## 5. 验证循环：让 Claude 自己检查自己的工作
- **来源**: [PrajwalTomar_ 的 Claude Code Playbook](https://x.com/PrajwalTomar_/article/2063238968125333581) on X | 🔥 引用 Boris Cherny 的研究
- **摘要**: 在 CLAUDE.md 中加入验证步骤，要求 Claude 在完成任务后自动运行测试或检查脚本。Boris Cherny 的研究表明，这种自验证循环能带来 2-3 倍的代码质量提升。关键是给 Claude 具体的验证命令，而不是抽象的"检查你的工作"。配合 hooks 可以实现自动化：编辑后自动格式化、提交前自动测试。
- **代码示例**:
```markdown
# CLAUDE.md 中添加验证规则：

## 验证要求
- 修改代码后，运行 `npm test` 确认没有破坏现有测试
- 添加新 API 端点后，运行 `npm run test:api` 验证
- 修改数据库 schema 后，运行 `npm run migrate:check`
```
```json
// .claude/settings.json - 添加自动格式化 hook
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "command": "npx prettier --write $CLAUDE_FILE_PATH"
    }]
  }
}
```

## 6. 用 /code-review 做 PR 审查，再让 Claude 自动修复
- **来源**: [wanerfu 的 Claude Code 技巧大合集](https://x.com/wanerfu/article/2113511840118612012) on X | 🔥 中文社区热帖
- **摘要**: 社区分享的高效工作流：先用 `/code-review` 命令对当前 diff 或 PR 进行代码审查，Claude 会列出潜在问题和改进建议。然后用 `--fix` 参数让 Claude 自动应用修复。配合 CodeRabbit 等第三方审查工具形成闭环：CodeRabbit 审查 PR → Claude Code 修复问题 → 重复直到 PR 通过。
- **代码示例**:
```bash
# 审查当前分支的改动
/code-review medium

# 审查并自动修复
/code-review medium --fix

# 审查特定 PR
/code-review high #42

# 完整闭环工作流：
# 1. 开发 → claude code 编写功能
# 2. 提交 PR → CodeRabbit 自动审查
# 3. claude code → /code-review --fix 修复问题
# 4. 重复步骤 2-3 直到 PR 通过
```

## 7. 子 Agent 的 effort 控制：10 月更新的精细调控
- **来源**: [wanerfu 的 Claude Code 技巧大合集](https://x.com/wanerfu/article/2113511840118612012) on X | 🔥 中文社区热帖
- **摘要**: 10 月 7 日更新（v2.1.292+）后，主会话可以为子 Agent 设置不同的 effort 级别。这意味着你可以让主 Agent 用高 effort 做架构决策，而让执行类子 Agent 用低 effort 快速完成简单任务。合理分配 effort 级别可以显著降低 token 消耗，同时不牺牲关键环节的质量。
- **代码示例**:
```javascript
// 在 workflow 脚本中为不同任务设置不同 effort
const review = await agent('审查这个文件的架构设计', {
  label: 'arch-review',
  effort: 'high'  // 关键决策用高 effort
});

const fixes = await parallel(
  review.findings.map(f => () =>
    agent(`修复: ${f.description}`, {
      label: `fix-${f.id}`,
      effort: 'low'  // 简单修复用低 effort
    })
  )
);
```
