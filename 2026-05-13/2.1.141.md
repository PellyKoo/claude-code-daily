## 1. Plan 模式 → 自动接受：Claude Code 创作者的核心工作流
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2007179832300581177) on X | 🔥 高互动创作者分享帖
- **摘要**: Claude Code 创建者 Boris Cherny 分享了自己的工作流：每次写 PR 都从 Plan 模式开始，与 Claude 反复讨论方案直到满意，然后切换到自动接受模式一次性完成编码。好的计划是高质量输出的关键，不要急于让 Claude 直接写代码。
- **代码示例**:
```bash

claude

# 2. 描述任务，Claude 会生成计划而非直接编码
> 我需要给用户模块添加角色权限系统

# 3. 反复调整计划
> 方案二更好，但需要考虑向后兼容
> 数据库迁移方案需要支持零停机

# 4. 计划满意后，切换到自动接受模式
# Shift+Tab 切换模式，一次性生成所有代码
```

## 2. 并行 Claude 实例：5+10 同时运行的高效模式
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2007179832300581177) on X | 🔥 高互动创作者分享帖
- **摘要**: Boris 透露他同时运行 5 个终端 Claude Code 实例，加上 5-10 个 claude.ai/code 网页实例，偶尔还通过 iOS 应用启动会话。每个实例处理不同任务或同一任务的不同方面，大幅提升吞吐量。关键是用 Git Worktree 隔离各实例的工作目录。
- **代码示例**:
```bash
# 使用 Git Worktree 为每个 Claude 实例创建隔离目录
git worktree add ../feature-auth feature/auth
git worktree add ../feature-api feature/api
git worktree add ../bugfix-perf bugfix/perf

# 终端 1：在 feature-auth 目录启动 Claude
cd ../feature-auth && claude

# 终端 2：在 feature-api 目录启动 Claude
cd ../feature-api && claude

# 网页端：在 claude.ai/code 打开更多实例
# 各实例互不干扰，最后合并分支即可
```

## 3. 验证反馈环：让 Claude 输出质量翻倍的秘诀
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2007179832300581177) on X | 🔥 高互动创作者分享帖
- **摘要**: Boris 强调获得 Claude Code 最佳结果的关键是"给 Claude 验证自身工作的方式"。当 Claude 能运行测试、查看构建输出、检查浏览器截图时，最终质量可以提升 2-3 倍。没有反馈环的纯生成模式容易产生累积错误。
- **代码示例**:
```bash
# 方式一：确保有完善的测试套件
# Claude 写完代码后会自动运行测试验证

# 方式二：在 CLAUDE.md 中要求验证
# CLAUDE.md:
# 修改任何组件后，运行 npm test -- --related
# 修改 API 后，用 curl 验证端点响应

# 方式三：使用 PostToolUse hook 自动验证
# .claude/settings.json:
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "command": "npm run typecheck && npm test -- --bail"
    }]
  }
}
```

## 4. 自定义状态栏：实时掌握 Token 和 Git 状态
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 8.3k stars
- **摘要**: Claude Code 底部状态栏可以深度自定义，显示当前模型、工作目录、Git 分支、未提交文件数和 Token 使用量。提供 10 种颜色主题可选。实时监控 Token 消耗有助于在上下文膨胀前及时 compact，避免智能降级。
- **代码示例**:
```jsonc
// ~/.claude/settings.json
{
  "statusLine": {
    "left": "{model} | {cwd}",
    "right": "🌿 {gitBranch} | 📝 {gitUncommitted} | 🔤 {tokensUsed}/{tokensMax}"
  }
}

// 或使用自定义脚本获取更多信息
// statusLine.right 支持 shell 命令：
// "right": "$(git log --oneline -1 --format='%s')"
```

## 5. Git Worktree：多分支并行开发的利器
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 8.3k stars
- **摘要**: Git Worktree 是 Claude Code 多实例并行工作的基础。与 `git stash` + `git checkout` 不同，Worktree 为每个分支创建独立的物理目录，多个 Claude 实例可以同时在不同分支上工作而互不干扰。完成后合并分支即可。
- **代码示例**:
```bash
# 列出当前 worktree
git worktree list

# 为新功能创建 worktree
git worktree add ../my-feature feature/new-api

# 在新 worktree 中启动 Claude Code
cd ../my-feature
claude

# 工作完成后清理
git worktree remove ../my-feature

# Claude Code 本身也支持 worktree 隔离的子代理：
# 在 CLAUDE.md 中可以配置子代理使用独立 worktree
```

## 6. 上下文管理：保持 40% 以下的黄金法则
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 53k stars
- **摘要**: 社区验证的经验法则：上下文使用率超过 40% 后 Claude 的推理质量开始下降。主动使用 `/compact` 带提示词压缩（告诉它保留什么），而不是等自动压缩触发。自动压缩往往丢失关键细节。不同话题应开新会话而非在旧会话中切换。
- **代码示例**:
```bash
# 使用 /compact 并附带提示，告诉 Claude 保留什么
/compact 保留当前的数据库迁移计划和已修改文件列表

# 查看当前上下文使用情况：观察状态栏的 token 计数
# 超过 40% → 立即 /compact
# 超过 60% → 考虑开新会话

# 不同任务用不同会话：
# 会话 1：处理后端 API
# 会话 2：处理前端组件
# 避免在一个会话中混合不相关的任务
```

## 7. 子代理委托模式：保持主上下文干净
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 53k stars
- **摘要**: 将研究性和探索性任务委托给子代理（subagent），只让最终结论返回主会话。主会话用 Opus 处理复杂推理，子代理可以用 Sonnet 执行聚焦任务。这样主上下文始终保持精简，不会被大量搜索结果和中间推理污染。
- **代码示例**:
```bash
# 设置子代理使用的模型
export CLAUDE_CODE_SUBAGENT_MODEL=claude-sonnet-4-6

# 在 CLAUDE.md 中定义子代理策略：
# 当需要搜索代码库时，委托给子代理执行
# 当需要阅读大文件时，委托给子代理提取摘要
# 主会话只接收最终结论

# 实际效果：
# - 主上下文保持干净，推理质量稳定
# - 子代理的搜索和阅读不消耗主会话 token
# - Sonnet 子代理成本更低，速度更快
```

## 8. 短会话 + 检查点提交：社区公认的最佳实践
- **来源**: [r/ClaudeAI](https://www.reddit.com/r/ClaudeAI/) on Reddit | 🔥 社区高频讨论共识
- **摘要**: Reddit 社区共识：短而专注的会话远胜于长时间马拉松式编码。每次让 Claude 自主工作前先提交一个 Git 检查点，如果结果不理想直接回滚重来，而不是在错误基础上修修补补。从头开始的成功率显著高于"修复前进"。
- **代码示例**:
```bash
# 最佳实践流程：
# 1. 提交检查点
git add -A && git commit -m "checkpoint: before Claude refactors auth module"

# 2. 给 Claude 明确、聚焦的任务
> 重构 auth 模块，将 JWT 验证逻辑抽取到独立中间件

# 3. 检查结果，不满意则回滚
git diff HEAD  # 查看所有变更
git stash      # 或暂存后重新尝试

# 4. 满意则提交
git add -A && git commit -m "refactor: extract JWT validation to middleware"

# 关键原则：
# - 每个会话只做一件事
# - 做之前先存档
# - 错了就重来，别修补
```
