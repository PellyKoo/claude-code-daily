## 1. 系统提示词裁剪：节省 50% Token 开销
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | 🔥 8.2k stars
- **摘要**: 通过补丁系统裁剪 Claude Code 内置的冗长工具描述，将系统提示词从约 19k Token 压缩至约 9k Token，节省近 50% 的固定开销。每次交互都能省下的 Token 可用于更多实际代码上下文，在长会话中效果尤为显著。
- **代码示例**:
```bash
# 查看当前系统提示词大小
claude --print-system-prompt | wc -w

# 使用 ykdojo 的补丁脚本裁剪系统提示词
# 详见 https://github.com/ykdojo/claude-code-tips (Tip 15)
```

## 2. 并行多 Claude 工作流：5+5 并发开发
- **来源**: [Matt Van Horn](https://x.com/mvanhorn/status/2035857346602340637) on X | 🔥 高热度传播
- **摘要**: 资深开发者的极限并行策略——在终端中开 5 个 Claude Code 实例，同时在 Web/手机端再开 5-10 个，每个实例使用独立的 Git checkout 避免文件冲突。适合大型重构或多模块并行开发，前提是任务之间相互独立且有清晰边界。
- **代码示例**:
```bash
# 为每个 Claude 实例创建独立的 worktree
git worktree add ../feature-auth feature/auth
git worktree add ../feature-api feature/api
git worktree add ../feature-ui feature/ui

# 在不同终端标签页中分别进入各 worktree 启动 Claude
cd ../feature-auth && claude
cd ../feature-api && claude
cd ../feature-ui && claude
```

## 3. Plan 模式工作流：先计划再自动执行
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2017742741636321619) on X | 🔥 Claude Code 创作者亲授
- **摘要**: Claude Code 创作者推荐的核心工作流：先进入 Plan 模式让 Claude 制定方案，反复讨论迭代直到计划令你满意，然后切换到自动接受模式让 Claude 一口气执行。这种方式能有效防止"Claude 跑偏"的问题，团队实测效率远超直接让 Claude 编码。
- **代码示例**:
```
# 步骤 1：进入 Plan 模式
> /plan 重构用户认证模块，从 session 迁移到 JWT

# 步骤 2：反复讨论、修正计划
> 不要改动现有 API 路由签名，需要向后兼容
> 增加 refresh token 的处理逻辑

# 步骤 3：计划确认后，开启自动接受
Shift+Tab 切换到 auto-accept 模式，让 Claude 执行计划
```

## 4. 交互式 PR 审查：对话式代码评审
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | 🔥 8.2k stars
- **摘要**: 利用 Claude Code 进行对话式代码审查，相比一次性输出的审查工具，可以控制审查节奏和深度。先让 Claude 概览 PR 变更，再逐文件深入讨论具体问题，对可疑代码直接追问"为什么这样实现"。
- **代码示例**:
```bash
# 让 Claude 审查当前分支的 PR
claude "审查这个 PR 的变更，先给出总体评价，
然后列出每个文件的关键问题。
重点关注：安全性、性能、错误处理"

# 针对具体文件深入追问
> src/auth/jwt.ts 中的 token 过期处理是否有竞态条件？
```

## 5. 每轮决策分支点：科学管理会话走向
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | 🔥 51.8k stars
- **摘要**: Anthropic 工程师 Thariq 提出的"分支点"概念：每完成一轮对话后，根据当前状态选择最优的下一步动作——继续对话、`/rewind` 回退、`/clear` 重置、`/compact` 压缩、或启动子代理。将会话管理从随意操作变成有意识的策略选择，显著提升复杂任务的成功率。
- **代码示例**:
```
# 决策树示意
完成一轮对话后 →
  ├─ 方向正确 → 继续对话
  ├─ 最后一步有误 → /rewind
  ├─ 上下文太乱 → /compact 保留关键信息
  ├─ 需要全新思路 → /clear 重新开始
  └─ 独立子任务 → 启动 subagent 隔离处理
```

## 6. 快速原型替代 PRD：低成本迭代 20-30 个版本
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2017742741636321619) on X / [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | 🔥 51.8k stars
- **摘要**: Claude Code 创作者的反直觉建议：不要花时间写详细的产品需求文档（PRD），直接让 Claude 快速构建原型。当实现成本足够低时，构建 20-30 个原型版本比写一份完美规格文档更高效。每个原型都是一次学习机会，让你在实物中发现真正需要什么。
- **代码示例**:
```bash
# 传统方式：写 PRD → 评审 → 开发（数天）
# Claude 方式：直接原型迭代（数小时）

# v1: 最简原型
claude "用 React 做一个看板组件，最简实现"
# v2: 加入拖拽
claude "加入拖拽排序功能，用 dnd-kit"
# v3: 加入持久化
claude "接入 API 持久化，乐观更新"
# 反复迭代直到满意...
```

## 7. 子代理隔离上下文：保持主会话清洁
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | 🔥 51.8k stars
- **摘要**: 在代码审查和复杂调查任务中，使用子代理（subagent）替代在主会话中直接执行。子代理的中间工具调用和探索过程完全隔离，只有最终结论返回主会话，有效防止大量中间信息污染主上下文。这是除 `/compact` 外最有效的上下文管理手段。
- **代码示例**:
```markdown
<!-- .claude/commands/review-isolated.md -->
使用子代理审查以下文件的变更：$FILES

子代理应该：
1. 逐文件检查代码质量和潜在问题
2. 运行相关测试验证正确性
3. 只将关键发现和建议返回主会话

不要将中间的文件读取和测试输出带回主上下文。
```

## 8. Skill 描述优化：用触发词而非摘要
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | 🔥 51.8k stars
- **摘要**: Anthropic 工程师建议 Skill 的描述不应是功能摘要，而应写成"触发词丰富"的描述——因为 Claude 通过语义匹配描述来决定何时应用 Skill。好的描述关注"什么场景下该触发"，而非"这个 Skill 做什么"。同时，描述应聚焦于推动 Claude 超越默认行为的指令，避免流水账式的步骤罗列。
- **代码示例**:
```markdown
<!-- ❌ 差的 Skill 描述 -->
这个 skill 用于部署应用到生产环境，包括构建、测试和推送步骤。

<!-- ✅ 好的 Skill 描述 -->
当用户说"部署"、"上线"、"发布到生产"、"push to prod"时触发。
也适用于 CI 通过后的自动发布流程。
必须在部署前运行完整测试套件并检查环境变量配置。
```
