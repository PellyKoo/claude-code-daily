## 1. CLAUDE.md 三级架构：全局、项目、本地分层管理
- **来源**: [abhishekray07/claude-md-templates](https://github.com/abhishekray07/claude-md-templates) on GitHub | ⭐ 315 stars
- **摘要**: 社区总结的 CLAUDE.md 三级配置架构：全局文件（`~/.claude/CLAUDE.md`）放个人偏好，项目文件（`.claude/CLAUDE.md`）放团队约定并提交 git，本地文件（`./CLAUDE.local.md`）放个人覆盖并 gitignore。核心原则是每层文件控制在 80 行以内，因为指令会和 Claude 自带的约 50 条系统指引竞争注意力。"人格指令"（如"做一个资深工程师"）纯属浪费 token。
- **代码示例**:
```bash
# 三级配置快速搭建
# 1. 全局：个人偏好（适用所有项目）
mkdir -p ~/.claude
cat > ~/.claude/CLAUDE.md << 'EOF'
- 修改代码后运行相关测试
- 优先使用已有工具而非新装依赖
- 提交前运行 typecheck
EOF

# 2. 项目：团队约定（提交到 git）
cat > .claude/CLAUDE.md << 'EOF'
- Stack: Next.js 15 + TypeScript + Prisma
- Test: pnpm vitest
- Lint: pnpm eslint --fix
EOF

# 3. 本地：个人覆盖（gitignore）
echo "CLAUDE.local.md" >> .gitignore
```

## 3. 自我纠正循环：用 Hook 实现自动运行测试和格式化
- **来源**: [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 6k stars, 567 forks
- **摘要**: 社区热门展示项目演示了完整的 Hook 驱动自动化流水线。关键洞察：让 Claude 在每次编辑文件后自动运行 prettier 格式化和测试，形成"写代码→自动格式化→自动测试→发现问题→修复"的闭环。结合 `PreToolUse` 阻止危险操作（如直接编辑 main 分支），构建安全且高效的自动化管道。PR 审查自动化成本仅约 $0.05-0.50/次。
- **代码示例**:
```jsonc
// .claude/settings.json — 完整自动化 Hook 配置
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "bash -c 'branch=$(git branch --show-current); [[ \"$branch\" == \"main\" || \"$branch\" == \"master\" ]] && echo BLOCK: 禁止直接编辑主分支 && exit 1 || exit 0'"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "npx prettier --write $CLAUDE_FILE_PATH && npm test -- --related --passWithNoTests"
      }
    ]
  }
}
```

## 4. 注意力预算问题：为什么你的 CLAUDE.md 没效果
- **来源**: [abhishekray07/claude-md-templates](https://github.com/abhishekray07/claude-md-templates) on GitHub | ⭐ 315 stars
- **摘要**: 社区发现了一个关键问题：你写的指令在和 Claude 自带的约 50 条系统级指引竞争"注意力预算"。如果 CLAUDE.md 超过 80 行，Claude 会开始忽略部分内容。解决方案：不要在 CLAUDE.md 里嵌入整个文档（`@docs/api.md` 会每次加载整个文件），改为告诉 Claude 什么时候去读；不要重复 linter 已经会做的格式化规则；用 `.claude/rules/*.md` 配合 YAML frontmatter 按文件类型懒加载规则。
- **代码示例**:
```yaml
# .claude/rules/api-routes.md — 按路径懒加载
---
globs:
  - "src/app/api/**/*.ts"
  - "src/routes/**/*.ts"
---
# API 路由规范
- 所有端点必须有输入验证（使用 zod）
- 错误响应使用统一格式 { error: string, code: number }
- 需要认证的路由使用 withAuth 中间件包装

# 不要在根 CLAUDE.md 里写这些！
# 它们只在编辑 API 文件时才需要加载
```

## 5. 三阶段工作流：Explore → Plan → Execute
- **来源**: [35+ Claude Code Tips (2026 Edition)](https://x.com/Suryanshti777/status/2029200211093201017) on X | 🔥 热门技巧合集
- **摘要**: 社区验证的最高效工作流——不要直接让 Claude 写代码。第一步让它研究代码库，理解现有架构和依赖；第二步进入 Plan Mode（`Shift+Tab`）制定结构化方案，此时审查和调整成本最低；第三步切回 Normal Mode 逐步执行。搭配 `/init` 命令在新项目中自动生成 CLAUDE.md 作为"项目大脑"，让每次后续会话都带着完整上下文启动。
- **代码示例**:
```bash
# 三阶段工作流实操

# 阶段 1：Explore（研究）
> "分析这个项目的认证系统，列出所有相关文件、用到的库和数据流"
# Claude 会搜索代码库、读取文件、理解架构

# 阶段 2：Plan（规划）— 按 Shift+Tab 进入
> "基于分析结果，制定将 session 认证迁移到 JWT 的方案"
# Claude 输出结构化步骤，你审查后调整

# 阶段 3：Execute（执行）— 按 Shift+Tab 切回
> "执行计划的第 1 步：创建 JWT 工具函数"
# 逐步执行，每步可验证

# 新项目初始化：让 Claude 自动生成项目大脑
> /init
# 自动生成包含架构、约定、命名规则的 CLAUDE.md
```

## 6. MCP 集成：一条命令串联 Jira、Slack、数据库
- **来源**: [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 6k stars
- **摘要**: 通过 `.mcp.json` 配置 MCP Server，让 Claude Code 直接访问 Jira/Linear（读需求）、Slack（发通知）、数据库（查数据），实现"读 Ticket → 分析需求 → 实现代码 → 更新状态 → 创建 PR"的全自动流水线。MCP 让 Claude Code 从单纯的代码编辑器进化为连接整个开发生态的中枢节点。
- **代码示例**:
```jsonc
// .mcp.json — MCP 集成配置
{
  "mcpServers": {
    "jira": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-jira"],
      "env": {
        "JIRA_URL": "https://your-team.atlassian.net",
        "JIRA_TOKEN": "${JIRA_API_TOKEN}"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-postgres"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    }
  }
}
// 用法："读取 PROJ-123 的需求，查询相关表结构，然后实现功能"
```

## 8. 40 个被忽视的 Claude 技巧和快捷方式
- **来源**: [Khairallah AL-Awady (@eng_khairallah1)](https://x.com/eng_khairallah1/article/2064997374242504863) on X | 🔥 热门长文
- **摘要**: 整理了 40 个大多数用户从未使用过的 Claude 技巧和快捷方式，涵盖提示优化、上下文管理、输出控制等多个维度。强调"垂直切片"开发法——一次贯穿所有层（API → Service → Controller → 前端）而非水平分层推进，能更早获得端到端反馈。同时推荐用 `/compact` 配合保留提示来精确控制上下文压缩保留什么信息。
- **代码示例**:
```bash
# 垂直切片 vs 水平分层

# ❌ 水平分层（容易失去上下文）
> "先写所有 API 路由"
> "再写所有 Service 层"
> "最后写前端"  # 此时已经忘了 API 的细节

# ✅ 垂直切片（推荐）
> "实现用户注册的完整流程：API 路由 → Service → 数据库 → 前端表单"
# 一次做完一个功能的所有层，立即可端到端测试

# 精确压缩上下文
/compact 保留：用户注册功能的 API 接口定义和数据库 schema
```
