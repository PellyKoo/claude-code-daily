# Claude Code 2.1.218 社区实用技巧 - 2026-07-23

## 1. AskUserQuestionTool 面试黑客：让 Claude 先问清楚再动手
- **来源**: [Filip Kowalski](https://x.com/filippkowalski/status/2010317972774994085) on X | 🔥 高互动病毒式传播帖
- **摘要**: 在 prompt 末尾加一句 "interview me in detail using the AskUserQuestionTool about literally anything: technical details, edge cases, UX preferences"，Claude 会在动手写代码之前疯狂提问——技术细节、边界条件、用户体验偏好全部问到。虽然"烦人地有用"，但这种方式能让 Claude 在真正编码前就理解你 90% 的需求，大幅减少返工。特别适合需求模糊或复杂功能的开发场景。
- **代码示例**:
```bash
# ❌ 直接下指令（Claude 会猜测你没说清楚的部分）
> Build a user authentication system

# ✅ 加上面试指令（Claude 先问清楚再动手）
> Build a user authentication system.
  Interview me in detail using the AskUserQuestionTool
  about literally anything: technical requirements,
  edge cases, security constraints, UX preferences,
  existing infrastructure, and deployment environment.

# Claude 会依次追问：
# - "你需要支持哪些登录方式？邮箱+密码？OAuth？SSO？"
# - "密码重置流程有什么特殊要求？"
# - "你的用户表是新建还是已有？用什么 ORM？"
# - "需要 MFA 吗？短信还是 TOTP？"
# - "Session 策略是 JWT 还是 cookie？过期时间？"
# 问完所有问题后，才开始编码——方案质量远超直接开工
```

## 2. 修复 Claude Code 偷懒：系统提示词里 5:1 的极简偏差
- **来源**: [Elie Steinbock](https://x.com/elie2222/status/2041477770245451885) on X | 🔥 高互动技术帖
- **摘要**: 社区发现 Claude Code 的系统提示词中有约 20 处指示"保持简洁/最小化"，但只有约 4 处鼓励"全面/彻底"——5:1 的比例天然偏向偷懒。Elie Steinbock 发布了一个 gist，通过在 CLAUDE.md 中添加反向指令来平衡这个偏差。核心思路是在项目级配置中明确要求 Claude "宁可多写也不要少写"、"实现完整功能而非最小示例"、"不要省略错误处理和边界检查"。应用后，Claude 的输出质量和完整度显著提升。
- **代码示例**:
```markdown
<!-- CLAUDE.md 中添加以下反偷懒指令 -->

<important>
## Code Completeness Rules

- Write COMPLETE implementations, never stubs or placeholders.
- Include ALL error handling, validation, and edge cases.
- When modifying a function, show the ENTIRE function, not just
  the changed lines.
- Do not use comments like "// ... rest remains the same" or
  "// existing code here" — write out the full code.
- When asked to build a feature, implement it fully rather than
  providing a "minimal example" that needs further work.
- Tests should cover happy path, error cases, AND edge cases.
- Prefer thoroughness over brevity in all code output.
</important>

<!-- 效果对比：
  修复前：Claude 经常输出 "// implement remaining cases..."
  修复后：Claude 输出完整实现，包含所有分支和错误处理 -->
```

## 3. 语音驱动开发：用嘴说代码需求，比打字快 3 倍
- **来源**: [ykdojo](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.4k stars
- **摘要**: 配合本地语音转文字工具（SuperWhisper、MacWhisper、Whisper.cpp），可以用语音输入替代键盘输入与 Claude Code 交流。实测语音输入速度约为打字的 3 倍，尤其适合描述复杂逻辑、解释 bug 上下文或口述架构设计。关键是选择支持"本地离线推理"的工具，避免把代码上下文发送到第三方服务器。SuperWhisper 支持设置快捷键，按住说话松开自动输入到 Claude Code 终端。
- **代码示例**:
```bash
# 推荐工具（macOS，均支持本地离线推理）
# 1. SuperWhisper - 最流行，支持快捷键触发
#    按住 Option 说话 → 松开 → 文字自动输入到当前窗口
brew install --cask superwhisper

# 2. MacWhisper - 支持批量转录和实时转录
brew install --cask macwhisper

# 3. Whisper.cpp - 开源免费，命令行工具
brew install whisper-cpp

# 使用场景：
# - 描述复杂 bug："这个问题是这样的，用户登录后如果在
#   30 秒内切换到设置页面，token 刷新会和路由守卫竞争..."
# - 口述架构："我想要一个事件驱动架构，用户操作发到
#   消息队列，消费者异步处理，失败的放到死信队列重试..."
# - 代码审查反馈："这个函数的命名不太好，getUser 其实
#   做了三件事，应该拆分成 fetchUser、validateUser、
#   transformUser..."

# 小技巧：在 SuperWhisper 设置中启用 "Code Mode"
# 它会自动识别编程术语，避免把 "React" 听成 "react"
```

## 4. 手机远程遥控 Claude Code：地铁上也能改 Bug
- **来源**: [ykdojo](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.4k stars
- **摘要**: Claude Code 内置 `/remote-control` 功能，启动后会生成一个二维码或链接，用手机扫描即可远程向电脑上运行的 Claude Code 发送指令。配合 `--dangerously-skip-permissions` 的 auto 模式，可以在手机上完全控制开发流程——查看代码、提交改动、运行测试。适合通勤途中处理简单 Bug、审查 PR、或在晚饭时突然想到一个改进点的场景。
- **代码示例**:
```bash
# 在电脑终端启动 Claude Code + Remote Control
claude --dangerously-skip-permissions
> /remote-control

# Claude 会输出：
# 📱 Remote Control URL: https://claude.ai/remote/abc123
# 📱 或扫描二维码连接

# 手机上打开链接后，可以直接输入指令：
# 📱 "Fix the failing test in auth.test.ts"
# 📱 "Run pnpm test and show me the results"
# 📱 "Create a PR for the current changes"

# 进阶用法：配合 Telegram 机器人
# 安装 claude-telegram-bridge 后，
# 可以直接在 Telegram 里给 Claude Code 发消息
# 📱 Telegram → Mac Mini → Claude Code → 代码改动
# 回到电脑时，所有改动和 plan 已经准备好了
```

## 5. /rewind 回退代替纠错：别让失败尝试污染上下文
- **来源**: [shanraisshan](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 63.4k stars
- **摘要**: 当 Claude Code 走错方向时，大多数人的本能是在当前对话中纠正它。但这会在上下文中留下"失败的尝试"和"纠正指令"的噪音，占用宝贵的上下文窗口并可能让后续推理受到干扰。正确做法是按两次 Esc 或输入 `/rewind` 回退到出错前的状态，然后用从失败中学到的经验重新 prompt。这样上下文保持干净，Claude 不会被之前的错误方向误导。
- **代码示例**:
```bash
# ❌ 在对话中纠正（上下文被污染）
> Build the payment flow with Stripe
  # Claude 用了过时的 Stripe API v2
> No, use Stripe API v3 with PaymentIntents
  # Claude 又搞混了 v2 和 v3 的混合代码
> That's wrong too. Let me explain...
  # 上下文已经充满了 3 轮失败尝试的代码
  # Claude 的注意力被分散在新旧代码之间

# ✅ 用 /rewind 回退后重新开始（上下文干净）
> Build the payment flow with Stripe
  # Claude 用了过时的 API
> [按两次 Esc 或输入 /rewind]
  # 回退到这条指令之前的状态

> Build the payment flow using Stripe API v3
  with PaymentIntents. Do NOT use deprecated
  Charges API. Reference: stripe.com/docs/payments/
  payment-intents
  # Claude 从零开始用正确的 API 实现
  # 上下文中没有任何失败尝试的干扰

# /rewind vs /clear 的区别：
# /rewind - 回退到上一步，保留之前的上下文
# /clear  - 清空所有上下文，从零开始
# 一般先试 /rewind，如果问题更深层再用 /clear
```

## 6. 每一步都做决策：Continue / Rewind / Clear / Compact / Subagent
- **来源**: [shanraisshan](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 63.4k stars
- **摘要**: 高效使用 Claude Code 的关键不是写更好的 prompt，而是在每一轮交互后有意识地做出"会话分支决策"。像下棋一样，每步后评估五个选项：继续当前对话、/rewind 回退重试、/clear 开新局、/compact 压缩节省空间、或 spawn subagent 将耗资源的任务隔离到子代理。大多数人只用"继续"，错过了 80% 的效率优化空间。
- **代码示例**:
```bash
# 每轮交互后的决策树

# 1. Continue（继续）- 一切顺利，接着来
#    适用：Claude 的输出符合预期，自然推进
> Great, now add error handling to this function

# 2. /rewind（回退）- 方向错了，带着经验重试
#    适用：Claude 偏离目标但上下文还有价值
> /rewind
> [用更精确的 prompt 重新尝试]

# 3. /clear（清空）- 推倒重来，全新会话
#    适用：上下文太混乱或需要完全不同的方案
> /clear
> [全新视角重新定义任务]

# 4. /compact（压缩）- 上下文快满了，压缩保留精华
#    适用：上下文使用率 >25%，还有更多工作要做
> /compact Focus on the auth module implementation.
  Discard the earlier database discussion.

# 5. Spawn Subagent（子代理）- 重活脏活让分身干
#    适用：探索性搜索、大量文件读取、代码考古
> Search the entire codebase for all usages of
  the deprecated UserService class. Use a subagent
  for this so it doesn't fill our context.

# 经验法则：
# - 3 轮无进展 → /rewind
# - 5 轮无进展 → /clear
# - 上下文 >25% → 考虑 /compact
# - 需要读 >10 个文件 → subagent
```

## 7. 交互式 PR 审查：让 Claude 当你的代码审查搭档
- **来源**: [ykdojo](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.4k stars
- **摘要**: 用 Claude Code 做 PR 审查时，不要一次性让它审查整个 PR。更好的方式是用交互式对话控制审查的节奏和深度——先让它概览变更范围，然后逐个文件深入讨论关键改动，对可疑代码追问"这里为什么这样写"或"这个改动会影响什么"。这种对话式审查比静态 AI 审查工具效果好得多，因为你可以即时引导 Claude 关注你最在意的方面。
- **代码示例**:
```bash
# 交互式 PR 审查工作流

# 第 1 步：概览（快速了解 PR 做了什么）
> Summarize the changes in this PR. Group by:
  - New features
  - Bug fixes
  - Refactoring
  - Test changes

# 第 2 步：重点文件深入审查
> Now review src/auth/token-refresh.ts in detail.
  Focus on:
  - Race conditions
  - Error handling completeness
  - Token expiry edge cases

# 第 3 步：追问可疑代码
> Why does line 45 use setTimeout instead of
  the existing retry utility? Is this intentional
  or a potential bug?

# 第 4 步：跨文件影响分析
> This PR changes the User type definition.
  Check all files that import User and verify
  they're compatible with the new shape.

# 第 5 步：生成审查意见
> Based on our review, write a GitHub review
  comment summarizing the 3 most important issues
  found, with suggested fixes for each.

# 对比传统方式：
# 一次性 "Review this PR" → 泛泛而谈，重点遗漏
# 交互式逐步深入 → 精准定位问题，审查质量提升 3-5 倍
```
