## 1. 多模型分工协作：Sonnet 主攻 + Haiku 搜索 + Opus 决策
- **来源**: [xsmryze (@xsmryze)](https://x.com/xsmryze/status/2116659187317186583) on X | 🔥 高互动热门推文
- **摘要**: xsmryze 分享了 Anthropic 推荐的多模型分工策略：同时运行 Sonnet、Haiku 5.5 和 Opus 5.5，让每个模型只做最擅长的事。Sonnet 作为主会话处理日常编码；Haiku 作为轻量级子代理并行执行文件搜索和代码扫描；Opus 作为"顾问"在关键架构决策时介入。这样不仅效果更好，token 消耗也更低，因为每个任务都落在了最合适的模型上。社区反响强烈，认为这是目前最高效的 Claude Code 使用模式。
- **代码示例**:
```bash
# 多模型分工配置思路

# 1. 主会话使用 Sonnet（速度快、性价比高）
# 处理日常编码、代码编辑、测试编写

# 2. 子代理使用 Haiku（最快最便宜）
# 适合并行扫描大量文件、搜索代码库
# Claude Code 内部的 Explore agent 等已自动使用轻量模型

# 3. 关键决策使用 Opus（最强推理能力）
# 架构设计、复杂 bug 诊断、代码审查
# 通过 /model 切换或在 settings 中配置 advisor 模型

# 核心原则：不是所有任务都需要最强模型
# 80% 的编码任务 Sonnet 足够
# 文件搜索等机械任务用 Haiku 省 token
# 只在需要深度思考时启用 Opus
```

## 2. 20 个高效快捷键与操作技巧
- **来源**: [Santiago (@svpino)](https://x.com/svpino/status/2050563493708112190) on X | 🔥 高转发实用技巧合集
- **摘要**: Santiago 整理了 20 个 Claude Code 使用技巧，其中最实用的快捷键包括：`Esc+Esc` 回溯会话到任意检查点（相当于免费的撤销，放心让 Claude 尝试激进改动）；`Ctrl+V` 直接粘贴截图到 Claude Code（无需保存文件再引用）；`Ctrl+G` 打开编辑器撰写长提示词（不用在终端中费劲编辑多行文本）。Santiago 强调 Rewind 功能被严重低估：当 Claude 走错方向时，不需要从头开始新会话，直接回溯到出错前的检查点继续即可，上下文完全保留。
- **代码示例**:
```bash
# Claude Code 高效快捷键速查

# Esc+Esc  → 回溯（Rewind）到任意检查点
#            可以放心让 Claude 尝试风险操作
#            不满意直接回溯，上下文完整保留

# Ctrl+V   → 粘贴截图/图片
#            报 bug 时直接截图粘贴最高效
#            Claude 会自动分析图片内容

# Ctrl+G   → 用外部编辑器写提示词
#            长指令、多步骤任务用编辑器写更方便
#            支持 $EDITOR 环境变量设定的编辑器

# Shift+Tab → 切换 Plan Mode
#            让 Claude 先出计划再动手
#            适合复杂任务的预审

# Tab       → 自动补全文件路径
#            在提示词中引用文件更快

# 实用工作流：
# 1. Shift+Tab 进入 Plan Mode 让 Claude 出方案
# 2. 审核方案后 Shift+Tab 切回执行
# 3. 如果执行结果不对 → Esc+Esc 回溯
# 4. 调整指令后让 Claude 重试
```

## 3. CLAUDE.md 速查表：结构化你的项目记忆
- **来源**: [Nick Babich (@101babich)](https://x.com/101babich/status/2067917641109418068) on X | 🔥 高互动教程推文
- **摘要**: Nick Babich 发布了一份 CLAUDE.md 速查表，将其比喻为"项目记忆 + 执行指南"。核心要点：CLAUDE.md 不是随意堆砌的笔记，而应该有清晰的结构——项目概述、代码架构、设计规范、执行规则四大板块。最关键的经验是：用"绝不"（Never）标记红线规则，用"总是"（Always）标记必须遵循的约定。保持文件在 200 行以内，超出部分拆分到子目录的 CLAUDE.md 中。他特别强调：好的 CLAUDE.md 能让新加入的开发者和 Claude 同时受益——它既是 AI 的配置文件，也是团队的活文档。
- **代码示例**:
```markdown
# CLAUDE.md 推荐结构模板

## 项目概述
# 一句话描述项目用途和技术栈
# 例：Next.js 14 电商平台，使用 Prisma + PostgreSQL

## 架构说明
# 关键目录结构和模块职责
# 只写 Claude 无法从代码推断的信息

## 开发命令
# npm run dev / npm test / npm run lint
# 数据库迁移：npx prisma migrate dev

## 代码规范
# Always: 所有新文件使用 TypeScript
# Always: 组件使用函数式写法 + hooks
# Never: 不要使用 any 类型
# Never: 不要直接操作 DOM

## 测试约定
# 单元测试：Jest + React Testing Library
# 每个新功能必须附带测试

## 注意事项
# 记录 Claude 容易犯的错误
# 例：这个项目的 API 路由在 /api/v2 不是 /api
```

## 4. Claude Code 创始人的使用建议：Auto Mode + 错误学习
- **来源**: [Boris Cherny (@bcherny)](https://x.com/bcherny/status/2017742741636321619) on X | 🔥 创始人亲自分享，极高互动
- **摘要**: Claude Code 的创始人 Boris Cherny 亲自分享了他和团队的使用技巧。最核心的建议：(1) 大胆使用 Auto Mode 而非逐步手动确认——Auto Mode 有独立的安全分类器保护，比你想象的安全；(2) 当 Claude 犯错时，不要只是纠正它，而是让它把错误记录到 CLAUDE.md 或创建一个 Skill，这样同样的错误不会再犯；(3) 使用 /goal 命令定义可衡量的目标，让 Claude 自动迭代直到达标。Cherny 特别提到：团队内部每个人用 Claude Code 的方式都不同，没有唯一正确的用法，关键是找到适合你工作流的模式。
- **代码示例**:
```bash
# Boris Cherny 推荐的工作流

# 1. 启用 Auto Mode（减少手动确认的打断）
# 在设置中选择 Auto 模式
# Auto Mode 使用独立的安全分类器
# 危险操作仍会被拦截

# 2. 让 Claude 从错误中学习
# 当 Claude 犯了一个错误后：
# "把你刚才犯的错误记录到 CLAUDE.md，
#  说明正确做法，避免下次再犯"

# 3. 使用 /goal 定义可衡量目标
/goal "所有测试通过且覆盖率 > 80%"
# Claude 会自动运行测试、分析失败、修复代码
# 循环迭代直到目标达成

# 4. 将重复性纠正转化为 Skill
# "把这个修复模式创建为一个 Skill，
#  以后遇到类似的类型错误自动应用"
```

## 5. Trail of Bits 安全团队的 Claude Code 配置
- **来源**: [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config) on GitHub | 🔥 知名安全公司开源配置
- **摘要**: 著名安全公司 Trail of Bits 开源了他们内部使用的 Claude Code 配置方案。核心理念：CLAUDE.md 中的文字指令是"建议性"的，Claude 在上下文压力下可能忽略，所以真正重要的安全规则必须用 Hooks 和 Settings 强制执行。他们的配置包含：(1) 严格的权限白名单，只允许必要的工具和命令；(2) PreToolUse Hook 拦截所有破坏性 Git 操作；(3) PostToolUse Hook 对每次文件修改自动运行 linter 和安全扫描。这套配置对处理敏感代码库的团队特别有参考价值——它展示了如何在保持 Claude Code 生产力的同时最大限度降低安全风险。
- **代码示例**:
```json
// Trail of Bits 风格的安全配置示例
{
  "permissions": {
    "allow": [
      "Read", "Grep", "Glob",
      "Edit", "Write",
      "Bash(npm test)", "Bash(npm run lint)",
      "Bash(git status)", "Bash(git diff)", "Bash(git log)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force*)",
      "Bash(curl*)",
      "Bash(wget*)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "echo \"$CLAUDE_TOOL_INPUT\" | grep -qE 'rm -rf|--force|--no-verify|DROP|DELETE FROM' && echo 'BLOCKED' >&2 && exit 1 || true"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "semgrep --config auto $CLAUDE_FILE_PATH 2>/dev/null || true"
      }
    ]
  }
}
```

## 7. 重建工作流：按创始人建议重构后的效果对比
- **来源**: [XDA Developers](https://www.xda-developers.com/rebuilt-my-claude-code-workflow-around-its-creators-advice/) | 🔥 技术媒体深度体验文章
- **摘要**: XDA Developers 的一篇深度文章记录了作者按照 Boris Cherny（Claude Code 创始人）的建议完全重构工作流后的体验。最大的改变是三点：(1) 从谨慎的手动确认切换到 Auto Mode，发现效率提升远超预期且安全分类器确实可靠；(2) 使用 /goal 命令替代手动逐步指导——定义一个可衡量的结果，让 Claude 自己决定实现路径；(3) 每次 Claude 犯错后立即让它更新 CLAUDE.md，几周后 Claude 在该项目上的表现明显改善。文章的结论是：大多数人低估了 Claude Code 的自主能力，过度干预反而降低效率。
- **代码示例**:
```bash
# 工作流重构前后对比

# ❌ 重构前：过度手动控制
# 1. 手动确认每个文件修改
# 2. 逐步给出详细指令
# 3. Claude 犯错后口头纠正
# 4. 每次新会话重复同样的上下文

# ✅ 重构后：信任 + 迭代学习
# 1. 启用 Auto Mode，只在真正危险时干预
# 2. 用 /goal 定义目标，让 Claude 自主规划
/goal "重构 auth 模块，所有现有测试通过，新增边界测试"
# 3. Claude 犯错后立即记录
# "把这个错误和正确做法写入 CLAUDE.md"
# 4. CLAUDE.md 积累项目知识，每次会话自动加载

# 效果：
# - 每个任务的确认次数从 ~15 次降到 ~3 次
# - 重复性错误在 2-3 次记录后基本消失
# - 复杂任务完成时间缩短约 40%
```
