## 1. Auto Mode：多任务并行的核心基础设施
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2058519809214607704) on X | 🔥 创造者亲授核心技巧
- **摘要**: Claude Code 创造者 Boris Cherny 分享他被问到最多的"第一技巧"：开启 Auto Mode。Auto Mode 消除所有权限确认弹窗，是实现"多 Claude 并行工作"的关键前提。核心工作流：启动一个会话后立即切换到另一个会话继续工作，Claude 在后台自动完成任务后通过系统通知提醒你。没有 Auto Mode，你会被困在一个终端里反复点确认。
- **代码示例**:
```bash
# 启用 Auto Mode 的方式

# 方式1：启动时指定
claude --allowedTools '*'

# 方式2：在会话中切换
# 按 Shift+Tab 切换到 Auto-accept 模式

# 方式3：在 settings.json 中预配置权限
{
  "permissions": {
    "allow": [
      "Read(**)", "Write(**)", "Edit(**)",
      "Bash(npm *)", "Bash(git *)",
      "Glob(**)", "Grep(**)"
    ]
  }
}

# Auto Mode + 多会话工作流
# Terminal 1: claude "重构 auth 模块"  → 后台运行
# Terminal 2: claude "修复 API bug"     → 后台运行
# Terminal 3: 你处理代码审查            → 通知来了再切换
```

## 2. CLAUDE.md 防御性编程：六条必写规则
- **来源**: [Santiago](https://x.com/svpino/status/2018682144361734368) on X | 🔥 高互动实操建议帖
- **摘要**: Santiago 分享了他在 CLAUDE.md 中必写的六条规则，核心理念是"防御性编程"：让 Claude 在动手前先描述方案等待批准；遇到模糊需求时主动提问而非猜测；每次只改最小范围避免"顺手重构"；修改前必须阅读整个文件而非只看片段；严格遵循现有代码风格；以及变更后自动跑测试。这套规则大幅减少了 Claude 的"惊喜操作"。
- **代码示例**:
```markdown
<!-- 添加到 CLAUDE.md 的六条防御性规则 -->

# 工作流规则
1. 写任何代码前，先描述方案并等待我的批准
2. 需求模糊时，先问清楚再动手，不要猜测
3. 只修改任务要求的部分，不要顺手重构无关代码

# 代码质量规则
4. 修改文件前必须阅读整个文件，理解完整上下文
5. 严格遵循项目现有的代码风格和命名规范
6. 每次变更后自动运行相关测试验证
```

## 3. Boris 十大 Power User 技巧：并行 Worktree 排第一
- **来源**: [Shruti Mishra](https://x.com/heyshrutimishra/status/2018368588432978151) on X | 🔥 高热度技巧解析帖
- **摘要**: Shruti 拆解了 Boris Cherny 公开的十大 Power User 技巧。排名第一的是并行 Worktree——同时运行 3-5 个 Claude 会话各自在独立的 git worktree 中工作，彼底互不干扰。这不只是"快一点"，而是一种完全不同的工作方式：你变成了多个 AI 工程师的项目经理，审核和指导而非亲自编码。关键是每个 worktree 对应一个独立的功能分支。
- **代码示例**:
```bash
# 并行 Worktree 完整设置

# 1. 创建多个 worktree（每个对应独立分支）
git worktree add ../project-auth feat/auth
git worktree add ../project-api feat/api-v2
git worktree add ../project-tests feat/test-coverage

# 2. 在每个 worktree 中启动独立的 Claude 会话
# Terminal 1:
cd ../project-auth && claude "实现 OAuth2 登录流程"

# Terminal 2:
cd ../project-api && claude "将 REST 端点迁移到 v2"

# Terminal 3:
cd ../project-tests && claude "为核心模块补充集成测试"

# 3. 完成后合并回主分支
cd ../project && git merge feat/auth
```

## 4. /last 30 days：一键社区调研的隐藏技能
- **来源**: [Startup Ideas Podcast](https://x.com/startupideaspod/status/2036896888507818099) on X | 🔥 热门技能发现帖
- **摘要**: 社区发现的一个强大 Claude Code Skill：`/last 30 days`。输入任意主题，它自动拉取 Reddit 帖子、X 推文、网页搜索结果，全部来自过去 30 天，然后综合成一份专家级回答。实质是一个多源信息聚合 + AI 综合分析的研究工作流。对于技术选型、竞品分析、社区趋势追踪等场景极为实用，省去了手动多平台搜索的时间。
- **代码示例**:
```bash
# /last 30 days 技能使用示例

# 在 Claude Code 会话中直接使用
/last 30 days React Server Components 最佳实践

# 自动执行的流程：
# 1. 搜索 Reddit 近30天相关讨论
# 2. 搜索 X/Twitter 近30天相关推文
# 3. 搜索网页近30天相关文章
# 4. 综合分析所有来源
# 5. 输出结构化的专家级回答

# 实用场景
/last 30 days Bun vs Deno 2026 性能对比
/last 30 days Next.js 15 迁移常见问题
/last 30 days PostgreSQL vs MySQL 2026 选型建议
```

## 5. Workflow 关键词陷阱：日常用词会意外触发大动作
- **来源**: [Matt Pocock](https://x.com/mattpocockuk/status/2061120343922614519) on X | 🔥 热门踩坑警告帖
- **摘要**: Matt Pocock（TypeScript 教育者）发现一个重要的坑：在 Claude Code 中说 "workflow" 这个词（比如 "创建一个 GitHub workflow"）会意外触发 Dynamic Workflows 模式，导致 Claude 启动大量子代理来完成任务。这意味着一个简单的 CI 配置请求会变成大规模的并行编排操作。解决方法：在不需要 Dynamic Workflows 时，避免在提示中使用 "workflow" 一词，改用 "pipeline"、"action" 等替代词。
- **代码示例**:
```bash
# ⚠️ 触发 Dynamic Workflows 的陷阱

# ❌ 这会触发 Dynamic Workflows（不是你想要的）
claude "创建一个新的 GitHub workflow 来运行 CI 测试"
# → Claude 启动子代理群，大规模并行操作...

# ✅ 用替代词避免误触发
claude "创建一个新的 GitHub Actions pipeline 来运行 CI 测试"
claude "创建一个新的 GitHub action 配置文件用于 CI"
claude "写一个 .github/actions CI YAML 配置"

# ✅ 如果必须用 workflow 一词，明确指定不要编排
claude "在 .github/workflows/ 目录下创建一个 YAML 文件，
       不需要启动子代理，这只是一个简单的配置文件"
```

## 6. Boris 团队的 CLAUDE.md 模板：社区可直接复用
- **来源**: [Hasan Toor](https://x.com/hasantoxr/status/2025851900911038603) on X | 🔥 高互动模板分享帖
- **摘要**: Hasan Toor 发现有人将 Boris Cherny 在 X 上公开分享的 Anthropic 内部工作流整理成了可直接使用的 CLAUDE.md 文件。核心内容包括：不猜测直接问、先写测试再实现、用 hooks 做自动验证、保持变更最小化。这个模板的价值在于它来自"造工具的人"实际每天使用的配置，而非理论推测。社区已经将其作为新项目的标准起点。
- **代码示例**:
```markdown
<!-- 基于 Boris 工作流的 CLAUDE.md 模板 -->

# 项目：{your-project-name}

## 命令
- 开发: npm run dev
- 测试: npm test
- 构建: npm run build
- Lint: npm run lint

## 工作原则
- 不确定时问，不要猜
- 先写失败的测试，再写让测试通过的代码
- 每次变更后运行 `npm test` 验证
- 只改需要改的，保持 diff 最小

## 代码规范
- 遵循项目现有风格
- 使用 TypeScript 严格模式
- 禁止 `any` 类型
- 错误处理使用 Result 模式
```

## 7. Claude Code Showcase：Hooks + Skills + Agents 完整参考实现
- **来源**: [ChrisWiles](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 5.9k stars，配置示范库
- **摘要**: 这个 5.9k stars 的仓库提供了 Claude Code 所有高级功能的完整参考实现：6 个专业 Skill（TDD、调试、React 模式等）、2 个 Agent（代码审查、GitHub 工作流）、6 个 Slash Command（onboard、ticket、PR 审查等）、以及 Hooks 自动化配置。最大亮点是内置的"技能评估系统"——通过关键词、文件路径和意图分析自动推荐相关 Skill，让你不需要记住所有可用技能。
- **代码示例**:
```json
// .claude/settings.json - Showcase 的 Hooks 配置
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write",
        "command": "echo '检查文件变更...'"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write",
        "command": "npx eslint --fix $CLAUDE_FILE_PATH"
      }
    ],
    "UserPromptSubmit": [
      {
        "command": "echo '评估是否有匹配的 Skill...'"
      }
    ]
  }
}
```
```bash
# Showcase 内置的 Slash Commands
/onboard        # 深入了解新任务上下文
/ticket         # JIRA/Linear 工单工作流
```

## 8. Claude Code 终极指南：带测验的分阶段学习体系
- **来源**: [FlorianBruniaux](https://github.com/FlorianBruniaux/claude-code-ultimate-guide) on GitHub | ⭐ 社区推荐深度指南
- **摘要**: 一份从入门到精通的 Claude Code 指南，独特之处在于它不只是文档，还包含测验和速查表。覆盖 Claude Code 全部功能：从基础命令到 Agentic Workflows 的完整学习路径。每章节后附有测验题帮助巩固理解。特别适合团队 onboarding——新成员可以按自己节奏学习，通过测验确认掌握程度后再进入下一阶段。附带的 cheatsheet 可打印贴在工位上快速参考。
- **代码示例**:
```bash
# 从终极指南中提炼的速查表（Cheatsheet）

# === 会话管理 ===
claude                     # 交互模式
claude "task"              # 直接任务模式
claude --print "query"     # 非交互查询
claude --continue          # 恢复上次会话
claude --resume            # 选择历史会话

# === 上下文控制 ===
/compact                   # 压缩当前上下文
/clear                     # 清空重新开始
@file.ts                   # 引用特定文件
/rewind                    # 回退到上个状态

# === 高级功能 ===
/init                      # 生成 CLAUDE.md
Shift+Tab                  # 切换权限模式
# .claude/skills/          # 技能定义目录
# .claude/settings.json    # 钩子和权限配置
```
