## 1. 保持上下文在 40% 以下以获得最佳效果
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 49.8k stars
- **摘要**: MLOps 社区的 Dex 建议将上下文使用率控制在 40% 以下，激进团队甚至控制在 30% 以内。超过此阈值后，模型响应质量会明显下降（context rot）。可通过自定义状态栏实时监控 token 使用百分比。
- **代码示例**:
```bash
# 使用 /compact 命令主动压缩上下文，而非依赖自动压缩
/compact "保留当前任务的关键上下文：正在修复认证模块的 bug"
```

## 3. 用 /compact 加提示词替代自动压缩
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 49.8k stars
- **摘要**: Anthropic 团队的 Thariq 指出，自动压缩时模型的智能程度最低。应该手动使用 `/compact` 并附带提示词，告诉它哪些上下文需要保留。在回退（rewind）之前先执行"从这里开始总结"，为下一轮迭代创建交接笔记。
- **代码示例**:
```bash
# 先总结关键信息，再压缩
/compact "保留：1) API 端点设计决策 2) 数据库 schema 变更 3) 待修复的测试用例"
```

## 5. 在 Docker 容器中运行 Claude Code 处理高风险任务
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 8k stars
- **摘要**: 对于实验性或高风险的自主任务，在隔离的 Docker 容器中运行 Claude Code 并使用 `--dangerously-skip-permissions` 标志。这样即使 Claude 执行了破坏性操作，也不会影响主系统。
- **代码示例**:
```bash
# 在 Docker 容器中安全地运行 Claude Code
docker run -it --rm \
  -v $(pwd):/workspace \
  -e ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY \
  claude-code --dangerously-skip-permissions
```

## 6. 拆分工作流：初始化代理 + 编码代理
- **来源**: [HackerRank](https://x.com/hackerrank/status/2016398850265935929) on X | 🔥 长线程讨论
- **摘要**: 将长期运行任务拆分为两个模式：初始化代理（Initializer Agent）负责项目搭建、功能清单、Git 设置和进度追踪；编码代理（Coding Agent）负责读取、实现和测试。这样可以避免丢失上下文和进度，同时减少 token 消耗。
- **代码示例**:
```markdown
<!-- CLAUDE.md 中定义两种模式 -->
## 初始化模式
- 创建项目结构
- 定义功能清单和验收标准
- 设置 Git 分支策略

## 编码模式
- 从功能清单中逐项实现
- 每完成一项就运行测试并提交
```

## 7. 用 /model 切换 Opus 做规划、Sonnet 做编码
- **来源**: [Boris Cherny](https://x.com/bcherny/status/2017742741636321619) on X | 🔥 Claude Code 创建者分享
- **摘要**: Claude Code 创建者 Boris Cherny 建议用 `/model` 命令在 Opus（深度推理）和 Sonnet（快速编码）之间切换。复杂架构决策和规划用 Opus，日常编码和重复性工作用 Sonnet，在推理深度和速度之间取得最佳平衡。
- **代码示例**:
```bash
# 规划阶段：切换到 Opus
/model opus
# "请分析这个微服务架构，设计数据库 schema"

# 编码阶段：切换到 Sonnet
/model sonnet
# "根据上面的设计，实现用户服务的 CRUD 接口"
```

## 8. 为每个 Skill 建立"踩坑记录"（Gotchas）
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 49.8k stars
- **摘要**: Anthropic 的 Thariq 建议在每个 Skill 中添加 "Gotchas" 部分，记录 Claude 在实际使用中的失败点。同时，Skill 的描述应该是模型的触发条件，而不是功能摘要——要为模型的激活时机而写，而非为人类阅读而写。
- **代码示例**:
```markdown
<!-- .claude/skills/deploy.md -->
# 部署技能

## 描述（触发条件）
当用户提到"部署"、"发布"、"上线"、"CI/CD"时激活

## Gotchas
- ⚠️ 不要在未运行测试的情况下部署
- ⚠️ 生产环境部署前必须检查环境变量
- ⚠️ Docker 镜像构建时注意 .dockerignore
```
