## 1. Esc+Esc 回滚：把每次编辑当免费试错
- **来源**: [Santiago (@svpino)](https://x.com/svpino/status/2050563493708112190) on X | 🔥 高传播推文（20 条技巧合集）
- **摘要**: Santiago 分享的 20 条 Claude Code 技巧中，Esc+Esc 回滚（Rewind）被社区反复引用。按两下 Esc 键可以回到之前任意一个 checkpoint，相当于免费的 undo。关键洞察：与其让 Claude 修复自己的错误（错误上下文会污染后续生成），不如直接回滚到出错前的状态重新来。这让你可以放心让 Claude 尝试激进方案——反正回退零成本。
- **代码示例**:
```bash
# 在 Claude Code 交互界面中：
# 1. Claude 做了一个不理想的修改
# 2. 按 Esc+Esc 打开 Rewind 面板
# 3. 选择要回滚到的 checkpoint
# 4. 调整提示词后重新尝试

# 为什么回滚优于"修复"：
# ❌ "Claude, 把刚才的修改改回去" → 错误上下文留在会话中，影响后续质量
# ✅ Esc+Esc 回滚 → 干净的上下文，重新出发
```

## 2. Workflow 脚本：让 Opus 写计划，廉价模型批量执行
- **来源**: [delost (@thedelost)](https://x.com/thedelost/status/2110472847084650726) on X | 🔥 高互动讨论
- **摘要**: 社区热议的大型任务处理模式：用 Opus 模型编写一个 Workflow 脚本作为执行计划，然后由一组较廉价的模型并行执行各个子任务。Opus 只负责规划和编排，不直接写代码，大幅降低了高端模型的 token 消耗。适合需要跨多文件、多模块协作的大型重构或迁移任务。社区称之为"架构师+工人"模式。
- **代码示例**:
```bash
# 概念流程：
# 1. 用 Opus 生成 Workflow 脚本（规划阶段）
# 2. Workflow 脚本 fork 出多个子 agent（执行阶段）
# 3. 每个子 agent 处理一个独立子任务

# 在 Claude Code 中使用 ultracode 关键词触发：
# "ultracode: 重构所有 API 端点从 REST 迁移到 GraphQL"

# Claude 会：
# 1. 分析所有需要迁移的端点
# 2. 编写 Workflow 脚本分配任务
# 3. 并行启动多个 agent 各自处理
# 4. 汇总结果并验证
```

## 3. Trail of Bits 安全配置：企业级 Claude Code 防护模板
- **来源**: [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config) on GitHub | 🔥 安全社区推荐仓库
- **摘要**: 安全公司 Trail of Bits 开源了他们的 Claude Code 配置模板，核心理念是：CLAUDE.md 中的指令可能在上下文压力下被"遗忘"，但 Hooks 和权限设置是确定性执行的。他们建议将安全关键规则（如禁止 `rm -rf`、强制代码审查）全部用 PreToolUse Hook 实现，而非写在 CLAUDE.md 中。仓库包含了完整的 settings.json 模板、安全 Hook 示例和团队协作规范。
- **代码示例**:
```json
// Trail of Bits 风格的安全 Hook 配置
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "echo \"$CLAUDE_TOOL_INPUT\" | python3 -c \"import sys,json; cmd=json.load(sys.stdin).get('command',''); sys.exit(1) if any(d in cmd for d in ['rm -rf','--force','--no-verify']) else sys.exit(0)\""
      }
    ]
  },
  "permissions": {
    "deny": ["Bash(rm -rf *)"]
  }
}
```

## 4. 定期审查你的 Skills：卸载重叠和过时的技能
- **来源**: [Prajwal Tomar (@PrajwalTomar_)](https://x.com/PrajwalTomar_/status/2074787074641899896) on X | 🔥 实用操作建议
- **摘要**: Prajwal 的建议引发社区共鸣：大多数开发者安装了一堆 Skills 却从不清理。过多的 Skills 会占用上下文窗口、增加 token 消耗，而且功能重叠的 Skills 可能产生冲突指令。他的方法是：列出所有已安装 Skills，对比实际使用频率，卸载从未触发过或与其他 Skill 重叠的技能。保持精简，只留真正提升工作流的 Skills。
- **代码示例**:
```bash
# 审查 Skill 的工作流：

# 1. 列出所有已安装的 skills
# 在 Claude Code 中输入 /skills 查看完整列表

# 2. 让 Claude 帮你分析
# "列出我所有已安装的 skills，
#  标记哪些功能重叠，
#  哪些从未被自动触发过，
#  建议我卸载哪些"

# 3. 精简原则：
# ✅ 保留：每天或每周触发的 skill
# ✅ 保留：有独特功能不可替代的 skill
# ❌ 卸载：与内置功能重叠的 skill
# ❌ 卸载：安装后从未触发过的 skill
```

## 5. 上下文管理黄金法则：40% 工作区，60% 压缩线
- **来源**: [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) on GitHub | 🔥 500+ Stars 社区指南
- **摘要**: 社区总结的上下文管理经验法则：争取让上下文使用量保持在 40% 以下，到达 60% 时就该考虑收尾当前任务。在切换到新任务前主动用 `/compact` 压缩上下文，而不是等到系统自动压缩（自动压缩的时机和质量不可控）。同时建议关闭 auto-compact，手动控制压缩时机，确保重要信息不会被意外丢弃。一个会话专注一个功能，避免"万能会话"的陷阱。
- **代码示例**:
```bash
# 上下文管理最佳实践：

# 1. 检查当前上下文使用量
# 在 Claude Code 中观察状态栏的上下文百分比

# 2. 在 40% 以下：自由工作
# 3. 到达 60%：考虑 /compact 或收尾任务
/compact

# 4. 切换任务时的正确流程：
/compact         # 先压缩当前上下文
# ...继续新任务...

# 5. 完全切换到不相关任务时：
/clear           # 清空开始新会话

# ❌ 反模式：一个会话做所有事
# ✅ 正确：一个功能一个会话，上下文保持精简
```

## 6. path-scoped Rules：让规则按路径自动加载
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub + [pexon-consulting 指南](https://github.com/pexon-consulting/claude-code-best-practices/blob/main/docs/anleitungen/claude-md.md) | 🔥 社区最佳实践共识
- **摘要**: 比子目录 CLAUDE.md 更优雅的方案：使用 `.claude/rules/` 目录存放带 `paths:` 前缀的规则文件。这些规则只在 Claude 操作匹配路径的文件时才会加载到上下文中。这比在每个子目录放 CLAUDE.md 更集中管理，也比把所有规则堆在根 CLAUDE.md 中更节省上下文。特别适合大型项目中不同模块有不同约定的场景（如前端 vs 后端、API vs 内部工具）。
- **代码示例**:
```markdown
# .claude/rules/api-conventions.md
---
paths:
  - src/api/**
  - src/routes/**
---
- 所有 API 端点使用 RESTful 命名
- 错误响应遵循 RFC 7807 格式
- 必须包含 OpenAPI 注释
```
```markdown
# .claude/rules/frontend-style.md
---
paths:
  - src/components/**
  - src/pages/**
---
- 使用函数组件 + hooks，不用 class 组件
- 样式使用 Tailwind CSS utility classes
- 组件文件使用 PascalCase 命名
```

## 7. /review 和 /simplify：提交 PR 前的自动质量把关
- **来源**: [marmelab 博客](https://marmelab.com/blog/2026/04/24/claude-code-tips-i-wish-id-had-from-day-one.html) + [builder.io 50 Tips](https://www.builder.io/blog/claude-code-tips-best-practices) | 🔥 社区博客高引用
- **摘要**: 社区发现 Claude 写的代码经常过度工程化——添加不必要的抽象层、过多的错误处理、冗余的类型定义。推荐的 PR 前工作流：先用 `/review` 对 diff 做代码审查找出潜在 bug，再用 `/simplify` 自动简化和清理过度工程化的部分。这两步可以替代部分人工 Code Review 的工作，确保提交的代码既正确又简洁。
- **代码示例**:
```bash
# PR 前的质量检查流程：

# 1. 功能开发完成后，先自审
/review          # 审查当前 diff 中的 bug 和问题

# 2. 根据审查结果修复问题后，简化代码
/simplify        # 自动清理过度工程化的代码

# 3. 最终检查
/review          # 再次确认简化后没有引入新问题

# 常见的过度工程化模式（/simplify 会处理）：
# - 不必要的抽象层和 wrapper
# - 过度的错误处理（catch 了不可能发生的错误）
# - 冗余的类型定义和接口
# - 过早优化的代码
```

## 8. Nick Babich 的 CLAUDE.md 速查表：结构化你的项目记忆
- **来源**: [Nick Babich (@101babich)](https://x.com/101babich/status/2067917641109418068) on X | 🔥 高转发实用帖
- **摘要**: Nick 分享了一个结构化 CLAUDE.md 模板被广泛转发。核心框架将 CLAUDE.md 分为五个明确的 section：项目概述（一句话说明项目是什么）、架构（关键目录和文件的用途）、约定（编码规范和命名约定）、工作流（构建、测试、部署命令）、陷阱（容易犯错的地方）。每个 section 限制在几行内，整体控制在 200 行以下。关键原则：如果 Claude 能从代码中推断出来的，就不要写进 CLAUDE.md。
- **代码示例**:
```markdown
# CLAUDE.md 结构化模板

## 项目概述
基于 Next.js 14 的电商平台，使用 Postgres + Prisma

## 架构
- src/app/ → App Router 页面和 API 路由
- src/lib/ → 共享工具函数和数据库客户端
- src/components/ → React 组件（按功能模块分目录）

## 约定
- 2 空格缩进，单引号，无分号
- 组件：PascalCase | 工具函数：camelCase
- API 响应统一用 { data, error, meta } 格式

## 工作流
- dev: `npm run dev` | test: `npm test` | lint: `npm run lint`
- 单个测试: `npm test -- --grep "test name"`

## 陷阱
- Prisma schema 修改后必须运行 `npx prisma generate`
- 环境变量在 .env.local 中，不要提交到 git
```
