## 1. Workflows：Claude Code 自 Skills 以来最大的能力升级
- **来源**: [Thariq (@trq212)](https://x.com/trq212/status/2061907538741006796) on X | 🔥 高互动讨论
- **摘要**: Anthropic 的 Thariq 深入介绍了 Workflows 功能，称其为自 Skills 和 Subagents 以来最大的能力升级。Workflows 允许用户编写确定性的编排脚本，通过 `agent()`、`parallel()`、`pipeline()` 等原语实现多智能体协同工作。特别值得关注的是它为非技术任务开辟的可能性——不仅限于代码，还可以用于研究、审计、文档生成等流程自动化。
- **代码示例**:
```javascript
// 多维度代码审查 Workflow 示例
export const meta = {
  name: 'review-changes',
  description: '多维度审查变更文件并验证每个发现',
  phases: [
    { title: 'Review' },
    { title: 'Verify' }
  ],
}
const DIMENSIONS = [
  { key: 'bugs', prompt: '查找潜在的 bug 和逻辑错误' },
  { key: 'perf', prompt: '查找性能问题和优化机会' }
]
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, { label: `review:${d.key}`, phase: 'Review' }),
  (review, d) => agent(`对抗性验证: ${review}`, {
    label: `verify:${d.key}`, phase: 'Verify'
  })
)
```

## 2. 上下文管理：40% 是"智力退化"的警戒线
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.8k stars
- **摘要**: 这个 GitHub 趋势榜第一的项目揭示了一个关键发现：当上下文使用达到约 40% 时，Claude 的"智力"会明显下降（"Dumb zone"）。在 1M 上下文模型上，退化大约在 300-400k token 时发生。建议：对于需要高智力的工作保持上下文在 30-40% 以下；主动使用 `/compact` 压缩而不是等自动触发；出错时用 `/rewind` 而不是让失败尝试留在上下文中污染后续推理。
- **代码示例**:
```bash
# 上下文管理最佳实践

# 新任务 → 新会话（别在旧上下文中堆积）
# 相关任务 → 可复用上下文

# 每个 turn 都是一个分支点，选择最佳策略：
# Continue   → 上下文健康，继续当前工作
# /rewind    → 回到检查点用新指令重试（比留着错误更好）
# /compact   → 主动压缩，保留关键信息
# /clear     → 彻底清空，新任务新开始
# Subagent   → 把重活交给子代理，主上下文只收结果

# 多 Claude 实例并行时用标签避免冲突
```

## 3. Skills 管理审计：别让 300 个 Skill 抢占上下文
- **来源**: [Prajwal Tomar (@PrajwalTomar_)](https://x.com/PrajwalTomar_/status/2074787074641899896) on X | 🔥 高互动
- **摘要**: 许多用户安装了大量 Skills 却不知道它们在相互竞争上下文空间。Prajwal 建议将一篇关于 Skills 的教程直接粘贴到会话中，让 Claude 审计你当前安装的所有 Skill，对比教程列表，卸载重叠的、从未触发的、或有更好版本的。核心理念：Skill 的描述决定了 Claude 何时激活它（语义匹配），所以描述要"触发词丰富"而非泛泛而谈。
- **代码示例**:
```bash
# Skills 审计流程

# 1. 列出当前所有已安装的 skills
> /skills

# 2. 让 Claude 进行审计
> "列出我所有已安装的 skill，分析每个的触发频率。
>  卸载以下类型：
>  - 功能重叠的（保留更好的那个）
>  - 从未触发过的
>  - 和内置能力重复的"

# 3. Skill 编写最佳实践
# - SKILL.md 控制在 500 行以内
# - 描述要包含丰富的触发词（Claude 用语义匹配决定何时激活）
# - 使用 context: fork 隔离执行，主上下文只看到最终结果
# - 包含 references/、scripts/、examples/ 子目录
```

## 4. 用量上限优化：理解滚动窗口机制
- **来源**: [Ruben Hassid (@rubenhassid)](https://x.com/rubenhassid/article/2043177416164815308) on X | 🔥 热门长文
- **摘要**: Claude 的用量限制采用滚动 5 小时窗口机制，而非每日重置。这意味着 5 小时前的用量会自动"滚落"释放配额。实用策略：将工作分为 2-3 个时段（早上、下午、晚上），让之前的用量在窗口中滚落；避免在短时间内密集使用；如果触发限制，等待最早那批用量滚落而非等 24 小时重置。
- **代码示例**:
```bash
# 用量管理策略

# 滚动窗口工作方式：
# |----5小时窗口----|
# 8:00 用了 30% → 到 13:00 这 30% 释放
# 10:00 用了 20% → 到 15:00 这 20% 释放

# 实用策略：
# 1. 分时段工作，每段 ~90 分钟
#    早上 8-10 → 午后 13-15 → 晚上 18-20
#
# 2. 高密度任务（大规模重构）安排在窗口开始
#
# 3. 触发限制时：查看最早的用量时间
#    等它过 5 小时滚落，而非等 24 小时
#
# 4. 低消耗任务（代码审查、小修改）穿插使用
```

## 5. 在 Claude Code 中运行 GPT-5.6 进行交叉审查
- **来源**: [Hamza Khalid (@humzaakhalid)](https://x.com/humzaakhalid/article/2076962991476527309) on X | 🔥 热门文章
- **摘要**: 通过 MCP 或自定义脚本将 OpenAI 的 GPT-5.6 Sol 集成到 Claude Code 工作流中，用于代码审查和批评环节。核心思路：让 Claude 写代码，然后用竞争模型做独立审查，形成交叉验证。这种多模型协作模式不是为了替代 Claude，而是利用不同模型的盲区差异来提高代码质量。
- **代码示例**:
```jsonc
// .mcp.json — 集成 OpenAI 模型做交叉审查
{
  "mcpServers": {
    "openai-reviewer": {
      "command": "npx",
      "args": ["-y", "mcp-openai-review"],
      "env": {
        "OPENAI_API_KEY": "${OPENAI_API_KEY}",
        "MODEL": "gpt-5.6-sol"
      }
    }
  }
}
// 工作流：
// 1. Claude 编写代码
// 2. "用 OpenAI 审查刚才的更改，重点看逻辑错误"
// 3. Claude 综合审查意见进行改进
```

## 6. 垂直切片开发法：一次贯穿所有层
- **来源**: [Khairallah AL-Awady (@eng_khairallah1)](https://x.com/eng_khairallah1/article/2064997374242504863) on X | 🔥 热门长文（40 个技巧合集）
- **摘要**: 在 40 个 Claude 技巧中最具实用价值的是"垂直切片"开发理念：让 Claude 一次贯穿所有层（API → Service → 数据库 → 前端）完成一个功能，而非水平分层逐步推进。水平方式的问题在于等做到第三层时，Claude 可能已经忘了第一层的细节。垂直切片能更早获得端到端反馈，减少上下文切换带来的信息损失。
- **代码示例**:
```bash
# 垂直切片 vs 水平分层

# ❌ 水平分层（上下文损失严重）
> "先写所有的数据库 migration"
> "再写所有的 API 路由"        # 开始忘 migration 细节
> "最后写前端页面"              # API 细节也模糊了

# ✅ 垂直切片（推荐）
> "实现用户注册的完整流程：
>  1. Prisma schema + migration
>  2. API 路由 + 输入验证
>  3. Service 层业务逻辑
>  4. React 表单 + 提交处理
>  5. 端到端测试"
# 一个功能全栈完成，立即可测试

# 大型功能拆分为多个垂直切片（tracer bullets）
# 每个切片都是可独立运行的最小完整功能
```

## 7. GitHub Actions 自动化：低成本 PR 审查机器人
- **来源**: [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 6k stars
- **摘要**: 通过 GitHub Actions 将 Claude Code 集成为自动化 PR 审查员。配置后每个 PR 自动触发代码审查，费用仅 $0.05-0.50/次。还可以设置定时任务：每周代码质量审查、每月文档对齐检查、每两周依赖审计。支持在 PR 评论中 `@claude` 触发交互式审查。这把人工代码审查从瓶颈变成了持续自动化流程。
- **代码示例**:
```yaml
# .github/workflows/claude-review.yml
name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Claude Code Review
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

# 定时维护任务
# schedule:
#   - cron: '0 9 * * 1'     # 每周一：代码质量审查
#   - cron: '0 9 1 * *'     # 每月1号：文档对齐
#   - cron: '0 9 1,15 * *'  # 每两周：依赖审计
```

## 8. 规则文件懒加载：按文件路径自动注入上下文
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 64.8k stars
- **摘要**: 不要把所有规则塞进根 CLAUDE.md（超过 200 行就开始被忽略）。改用 `.claude/rules/*.md` 文件，通过 YAML frontmatter 的 `globs` 字段指定适用路径，实现按需懒加载。只有当 Claude 操作匹配路径的文件时，相关规则才会被注入上下文。这解决了"注意力预算"问题——Claude 的指令和系统自带的约 50 条指引竞争，更少但更精准的规则比庞大的规则手册有效得多。
- **代码示例**:
```yaml
# .claude/rules/react-components.md
---
globs:
  - "src/components/**/*.tsx"
  - "src/components/**/*.ts"
---
# React 组件规范
- 使用函数组件 + hooks，不用 class 组件
- 每个组件文件导出一个主组件
- Props 使用 interface 定义，命名为 {ComponentName}Props
- 加载状态和错误状态必须处理

# .claude/rules/database.md
---
globs:
  - "prisma/**/*"
  - "src/db/**/*"
  - "src/**/*.repository.ts"
---
# 数据库规范
- Migration 必须可回滚
- 查询使用参数化防止 SQL 注入
- 大表操作必须有索引策略
```
