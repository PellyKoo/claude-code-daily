## 1. Dynamic Workflows：用 "ultracode" 触发多 Agent 编排
- **来源**: [Akshay (@akshay_pachaar)](https://x.com/akshay_pachaar/status/2060413985925820525) on X | 🔥 高互动技术解析帖
- **摘要**: 随 Opus 4.8 一起发布的 Dynamic Workflows 功能允许 Claude Code 编写编排脚本，将任务拆分给多个子 Agent 并行处理。在提示中加入 "ultracode" 关键字或在设置中开启即可触发。Claude 会自动生成 `pipeline()` 和 `parallel()` 调用来协调工作流。社区反馈：非常适合大规模重构和跨文件代码审查，但 token 消耗显著增加，建议先在小范围任务上试用。
- **代码示例**:
```bash
# 在提示中包含 ultracode 关键字触发
> ultracode 重构整个 auth 模块，拆分 JWT 验证、session 管理和权限控制

# 或在设置中启用
/config  # 找到 Dynamic workflow size 设置调整

# Claude 会自动生成类似这样的编排脚本：
# pipeline(dimensions, review_agent, verify_agent)
# 多个子 Agent 并行处理不同维度的任务
```

## 4. 在 60% 上下文容量时执行 /compact，而非等到 95%
- **来源**: [MindStudio 社区指南](https://www.mindstudio.ai/blog/tag/workflows/4) | 🔥 社区高赞实践建议
- **摘要**: 社区总结的关键发现：大多数人等到 Claude 自动压缩（接近上下文上限时）才处理，但此时已经丢失了大量重要细节。最佳实践是在上下文使用到约 60% 时主动执行 `/compact`，这时候压缩效果最好，关键信息保留率最高。配合自定义摘要提示（如 `/compact "保留数据库设计决策"`），可以精确控制保留哪些上下文。
- **代码示例**:
```bash
# 在完成每个子任务后主动压缩
/compact

# 指定保留重点信息
/compact "保留所有 API 接口设计的讨论和决定"

# 推荐节奏：
# 完成功能 A → /compact → 完成功能 B → /compact
# 而不是：做完 A+B+C → 上下文爆满 → 被迫自动压缩
```

## 5. 用 @文件名 精确约束 Claude 的关注范围
- **来源**: [Santiago (@svpino)](https://x.com/svpino/status/2029645889980305777) on X | 🔥 Sonar Summit 演讲精华
- **摘要**: Santiago 在 Sonar Summit 演讲中分享的 18 条技巧之首：始终用 `@filename.py` 或 `@src/classes/` 直接引用文件来约束 Agent 的工作范围。不引用文件时 Claude 会花大量 token 搜索和猜测相关文件；明确引用后，它直接聚焦到正确的上下文，响应更快、结果更准。这个简单的习惯可以显著减少 token 消耗和错误率。
- **代码示例**:
```bash
# 不推荐：模糊描述
> "修复登录功能的 bug"

# 推荐：用 @ 引用具体文件
> "修复 @src/auth/login.ts 中第 42 行的空指针异常"

# 引用整个目录
> "重构 @src/api/ 目录下所有路由的错误处理"

# 引用多个相关文件
> "在 @src/models/user.ts 中添加 email 字段，
#  并更新 @src/api/users.ts 的创建接口"
```

## 6. Boris Cherny 的验证循环法：质量提升 2-3 倍
- **来源**: [Boris Cherny（Claude Code 创建者）via whyaiman.substack.com](https://whyaiman.substack.com/p/tips-for-working-with-claude-code) | 🔥 创始工程师亲述
- **摘要**: Claude Code 的创建者 Boris Cherny 强调：给 Claude 提供验证手段是提升输出质量最重要的因素。具体做法是让 Claude 写完代码后立即运行测试、类型检查或其他验证命令，然后根据结果自我修正。社区多位开发者验证了这一方法，报告质量提升 2-3 倍。关键是在 CLAUDE.md 中明确写出验证命令，让 Claude 每次修改后自动执行。
- **代码示例**:
```markdown
# CLAUDE.md 中的验证规则示例
## 每次修改代码后必须执行
- `npm test -- --testPathPattern=<修改的模块>`
- `npx tsc --noEmit`
- `npx eslint --fix <修改的文件>`

## 验证循环流程
# 1. Claude 写代码
# 2. 自动跑测试 → 失败 → 修复 → 再跑测试
# 3. 直到所有检查通过才提交
```

## 7. Remote Control + tmux：断网也不怕的弹性会话
- **来源**: [Matt Van Horn (@mvanhorn)](https://x.com/mvanhorn/article/2035857346602340637) on X | 🔥 长文工作流分享
- **摘要**: 高级工作流技巧：在家里或服务器上的 tmux 会话中运行 Claude Code，然后通过 `claude remote-control` 从手机、平板或任何浏览器远程控制。即使 WiFi 断开（比如飞机上），tmux 中的 Claude 会话继续运行。回来后重新连接即可查看结果。特别适合长时间运行的重构任务和需要在多个设备间切换的场景。
- **代码示例**:
```bash
# 在服务器或家用机上
tmux new -s claude-work
claude  # 在 tmux 会话中启动 Claude Code

# 断开连接（Ctrl+B, D）后 Claude 继续运行

# 从手机或其他设备远程控制
claude remote-control

# 回来后重新连接
tmux attach -t claude-work
# 所有工作进度完好无损
```

## 8. Plan 模式：先规划再执行，避免走弯路
- **来源**: [Axel (@Axel_bitblaze69)](https://x.com/Axel_bitblaze69/article/2037978621684621428) on X | 🔥 两个月深度使用心得
- **摘要**: 作者在使用 Claude Code 两个月后的核心感悟：对于多文件修改或不熟悉的代码库，先进入 Plan 模式让 Claude 生成方案并反复迭代，直到满意再允许它写代码。虽然规划阶段多花几分钟，但能避免 Claude 在错误方向上浪费大量 token。小任务（单文件改几行）可以跳过规划直接执行。判断标准：如果你不确定改动会影响几个文件，就用 Plan 模式。
- **代码示例**:
```bash
# 进入 Plan 模式（连按两次 Shift+Tab）
# Claude 只分析和规划，不写代码

# Plan 模式下的对话示例：
> "分析 @src/auth/ 目录，规划如何将 session 管理从
#  Redis 迁移到 PostgreSQL，列出所有受影响的文件"

# Claude 输出方案后，反复迭代：
> "考虑并发场景怎么处理？"
> "migration 步骤是什么？"

# 满意后切回执行模式（再按 Shift+Tab）
# Claude 按照讨论好的方案开始写代码
```
