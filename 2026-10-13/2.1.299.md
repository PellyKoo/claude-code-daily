## 1. Plan 模式优先：先规划再编码
- **来源**: [Marmelab](https://marmelab.com/blog/2026/04/24/claude-code-tips-i-wish-id-had-from-day-one.html) on Blog | 🔥 高人气博文
- **摘要**: Marmelab 团队强烈推荐在动手写代码前先使用 Plan 模式。纠正一个计划比回退一个半成品功能容易得多。面对不熟悉的代码库时，先让 Claude 阅读代码并制定方案，确认后再执行，可以大幅减少返工。把 Claude 当作有上下文窗口限制的结对编程伙伴，而非全知的代码生成器。
- **代码示例**:
```bash
# 在 Claude Code 中使用 Plan 模式
> 先帮我分析这个模块的架构，制定重构方案，不要动代码
# Claude 会输出详细计划
# 确认后再让它执行
> 方案没问题，请执行
```

## 2. 上下文管理：/clear 和 /compact 的正确使用时机
- **来源**: [Data Science Collective](https://medium.com/data-science-collective/effective-claude-code-workflows-in-2026-what-changed-and-what-works-now-c93ebc6f8f50) on Medium | 🔥 热门工作流文章
- **摘要**: 当 Claude 犯了错误时，不要在错误的上下文中继续工作。错误的回复会留在上下文中，污染后续的尝试。正确做法是使用 `/clear` 清空上下文重新开始，或者用 `Esc+Esc` 回退到错误之前的检查点。在不相关的任务之间也应清理上下文，避免前一个任务的信息干扰新任务。长对话中定期使用 `/compact` 压缩历史。
- **代码示例**:
```bash
# 发现 Claude 走错方向时
Esc+Esc          # 回退到正确的检查点
/clear            # 或者完全清空重来

# 长对话中压缩上下文
/compact          # 保留关键信息，释放上下文窗口

# 切换不相关任务前
/clear            # 避免上下文交叉污染
```

## 3. Git Worktrees 实现多会话并行开发
- **来源**: [Kunal Ganglani](https://www.kunalganglani.com/blog/ai-coding-workflow-2026) on Blog | 🔥 高互动工作流分享
- **摘要**: 利用 Git worktree 可以让多个 Claude Code 会话同时在不同分支上工作，互不干扰。一个会话开发新功能，另一个写测试，第三个修 bug——全部并行进行。每个 worktree 是独立的工作目录，共享同一个 Git 仓库。这种模式特别适合需要快速迭代的团队，可以将开发效率提升数倍。
- **代码示例**:
```bash
# 创建多个 worktree 并行工作
git worktree add ../feature-auth feature/auth
git worktree add ../fix-bug-123 fix/bug-123
git worktree add ../write-tests test/api-tests

# 在不同终端中分别启动 Claude Code
cd ../feature-auth && claude
cd ../fix-bug-123 && claude
cd ../write-tests && claude

# 完成后清理
git worktree remove ../feature-auth
```

## 4. Hooks 做强制执行，CLAUDE.md 做行为引导
- **来源**: [codewithmukesh](https://codewithmukesh.com/blog/claude-code-tips-advanced/) on Blog | 🔥 .NET 开发者高赞指南
- **摘要**: CLAUDE.md 中的指令是"建议性"的，Claude 可能忽略。而 Hooks 是确定性执行的——每次工具调用后自动触发，不依赖 Claude 的"记忆"。最佳实践是将格式化、lint 等必须执行的步骤放在 Hooks 中（如 `PostToolUse` 钩子），而将编码风格偏好、架构约定等放在 CLAUDE.md 中作为指导。
- **代码示例**:
```json
// .claude/settings.json - PostToolUse Hook 示例
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "dotnet format --include $CLAUDE_FILE_PATH"
      }
    ],
    "PreCommit": [
      {
        "command": "dotnet test --no-build"
      }
    ]
  }
}
```

## 5. 语音输入驱动 Claude Code 开发
- **来源**: [mvanhorn](https://x.com/mvanhorn/article/2035857346602340637) on X | 🔥 创意工作流热帖
- **摘要**: 使用语音转文字工具（如 macOS 听写或 Whisper）将语音直接输入到 Claude Code 终端，实现"说话编程"。特别适合在构思阶段快速表达想法——比如口述功能需求、描述 bug 现象、或者解释重构意图。搭配远程 tmux 会话使用，即使在移动中也能继续开发。会议结束后直接将会议记录粘贴给 Claude，让它生成实施方案。
- **代码示例**:
```bash
# macOS 内置听写
# 按 Fn+Fn 启动听写，直接对着麦克风说需求

# 或使用 Whisper 管道
whisper --model small --language zh | claude

# 会议记录 → 实施方案
> 以下是今天产品会议的记录：[粘贴内容]
> 请提取所有技术任务，生成实施方案和优先级排序
```

## 6. CLAUDE.md 分层架构：从组织到子目录
- **来源**: [baeseokjae](https://baeseokjae.github.io/posts/claude-md-setup-guide-2026/) on Blog | 🔥 详细配置指南
- **摘要**: CLAUDE.md 支持多层级配置，从上到下依次为：组织级（统一策略）→ 用户全局级（个人偏好）→ 项目根目录（项目约定）→ 子目录级（模块特定规则）。Monorepo 项目特别受益于这种分层——根目录放通用规则（如提交规范、CI 要求），各子包放各自的技术栈约定。规则要具体而非模糊，并且附上原因帮助 Claude 在边界情况下做出正确判断。
- **代码示例**:
```
项目结构示例：
~/.claude/CLAUDE.md                    # 用户全局：个人偏好
./CLAUDE.md                            # 项目根：通用规则
./packages/frontend/CLAUDE.md          # 前端子包
./packages/backend/CLAUDE.md           # 后端子包
./packages/shared/CLAUDE.md            # 共享库

# 项目根 CLAUDE.md 示例
## 提交规范
- 使用 Conventional Commits 格式
- 原因：CI 自动生成 changelog 依赖此格式

## 测试要求
- 所有 PR 必须包含测试
- 运行命令：pnpm test
```

## 7. 并行代理工作流加速大规模任务
- **来源**: [willowvoice](https://willowvoice.com/blog/claude-code-parallel-agent-workflows) on Blog | 🔥 September 2026 实战指南
- **摘要**: Claude Code 的并行代理（Parallel Agent）工作流可以将大型任务拆分为多个子任务同时处理。例如代码审查时，可以让不同代理分别检查 bug、性能问题和安全漏洞，然后汇总结果。关键技巧是合理拆分任务粒度——太粗会失去并行优势，太细会增加协调开销。配合 `--worktree` 标志使用，每个代理在独立的工作树中运行，避免文件冲突。
- **代码示例**:
```bash
# 在 Claude Code 中触发并行工作流
> 使用 workflow 对所有变更文件进行并行审查：
> - 代理 1：检查逻辑错误和边界条件
> - 代理 2：检查性能问题和内存泄漏
> - 代理 3：检查安全漏洞和输入验证

# 或使用 CLI 批量处理
claude -p "审查 src/api/ 下所有文件的错误处理" --worktree &
claude -p "审查 src/api/ 下所有文件的性能问题" --worktree &
wait
```
