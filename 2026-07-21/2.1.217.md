# Claude Code 2.1.217 社区实用技巧 - 2026-07-21

## 1. 自我改进循环：让 CLAUDE.md 自动进化
- **来源**: [abhishekray07](https://github.com/abhishekray07/claude-md-templates) on GitHub | ⭐ 294 stars
- **摘要**: 每次 Claude 犯错后，不要只纠正当前错误，而是要求它同时更新 CLAUDE.md 防止同类错误再次发生。这个「自我改进循环」可以让你的项目配置随使用迭代优化，无需手动维护。核心命令：纠正错误后追加一句 "Update CLAUDE.md so you don't make that mistake again"。长期使用后，CLAUDE.md 会自动积累项目的隐性知识和常见陷阱。
- **代码示例**:
```bash
# 自我改进循环实战
# 1. Claude 犯了一个错误（比如用了错误的导入路径）
> Fix the import path, and update CLAUDE.md
  so you don't make that mistake again.

# Claude 会同时：
# - 修复当前代码
# - 在 CLAUDE.md 中添加类似这样的规则：
# ## Import Conventions
# - Use @/components/ for shared components
# - Use relative paths only within the same module
# - Never import from src/ directly

# 2. 几周后你的 CLAUDE.md 会自动积累：
# - 项目的隐性规则
# - 常见陷阱和解决方案
# - 团队约定的最佳实践
```

## 2. Skill 描述是写给模型看的触发器，不是写给人看的说明
- **来源**: [shanraisshan](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 63.3k stars
- **摘要**: 大多数人把 skill 的 description 字段当人类可读的功能说明来写，但实际上它是模型用来决定"何时触发这个 skill"的判断依据。应该把 description 写成面向模型的触发条件描述，比如 "when the user asks to review a PR or mentions code review"。同时，在 skill 中添加 `gotchas` 部分记录使用中发现的失败场景，这是迭代中信号密度最高的内容。
- **代码示例**:
```markdown
<!-- .claude/skills/testing-patterns.md -->
---
description: >
  Use when the user asks to write tests, fix failing tests,
  or when editing files that have corresponding .test.ts files.
  Also trigger when user mentions TDD, coverage, or mocking.
---

## Testing Patterns

### Approach
- Use describe/it with clear test names
- Mock external deps at module level
- Arrange-Act-Assert structure

### Gotchas (从实际使用中积累)
- ❌ Don't use jest.mock() inside test blocks
- ❌ Don't forget to clearAllMocks in afterEach
- ❌ Async tests must await or return the promise
```

## 3. HTML 注释在 CLAUDE.md 中零 token 消耗——隐藏指导不占上下文
- **来源**: [centminmod](https://github.com/centminmod/my-claude-code-setup) on GitHub | ⭐ 2.5k stars
- **摘要**: CLAUDE.md 中的 HTML 注释 (`<!-- -->`) 在运行时会被剥离，不消耗任何 token。这意味着你可以在 CLAUDE.md 中大量使用 HTML 注释来存放维护说明、变更历史、设计决策等元信息，而不会影响宝贵的上下文窗口。这个技巧让你在保持 CLAUDE.md 精简的同时，保留完整的项目文档。
- **代码示例**:
```markdown
<!-- CLAUDE.md -->
# Project Rules

<!-- 维护说明（零 token 消耗）:
  - 2026-07-15: 添加了 API 限流规则
  - 2026-07-10: 移除了旧的 ESLint 配置
  - 设计决策: 选择 Tailwind 而非 CSS Modules
    原因: 团队投票 + 与 shadcn/ui 兼容性更好
-->

## Stack
- Next.js 15, TypeScript, Tailwind CSS

<!-- 这段注释不会消耗 token，但帮助人类维护者理解规则背景 -->
## DO NOT
- Do not use CSS Modules
- Do not add console.log in production code
```

## 4. Skill-Eval Hook：根据 prompt 内容自动匹配并建议 Skill
- **来源**: [ChrisWiles](https://github.com/ChrisWiles/claude-code-showcase) on GitHub | ⭐ 6k stars
- **摘要**: 通过 `UserPromptSubmit` hook 配合 `skill-eval.js` 脚本，实现智能 skill 自动匹配。每次用户输入 prompt 时，hook 会分析关键词、文件路径和意图模式，自动建议最相关的 skill。这消除了"我有 20 个 skill 但总忘记用哪个"的问题。配合定时 GitHub Actions（每周质量扫描、每月文档同步、双周依赖审计），形成完整的自动化开发工作流，月成本仅 $10-50。
- **代码示例**:
```jsonc
// .claude/settings.json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "command": "node .claude/hooks/skill-eval.js \"$PROMPT\"",
        "description": "分析 prompt 并建议相关 skill"
      }
    ]
  }
}

// .claude/hooks/skill-rules.json（匹配规则示例）
{
  "rules": [
    {
      "skill": "testing-patterns",
      "keywords": ["test", "spec", "coverage", "mock", "TDD"],
      "paths": ["**/*.test.ts", "**/*.spec.ts"]
    },
    {
      "skill": "systematic-debugging",
      "keywords": ["bug", "error", "debug", "fix", "broken"],
      "intent": ["investigate", "diagnose"]
    }
  ]
}
```

## 5. 上下文腐烂阈值：30% 主动 compact，别等到 40% 自动压缩
- **来源**: [shanraisshan](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | ⭐ 63.3k stars
- **摘要**: 社区经验表明 Claude Code 会话在 300-400k token 后开始质量衰减（"上下文腐烂"）。老手的做法是在上下文使用率达到 30% 时就主动执行 `/compact`，并在 compact 命令中明确指定要保留的关键信息。等到 40% 自动压缩时，模型往往已经开始丢失重要上下文。另一个关键洞察：每个 turn 都是决策分岔点——成功就继续，失败就 `/rewind`，话题切换就 `/clear`，上下文膨胀就 `/compact`。
- **代码示例**:
```bash
# 上下文管理策略

# ✅ 在 30% 时主动 compact（带保留指令）
> /compact Keep: auth flow decisions, DB schema v2,
  API endpoint naming conventions, the failing test context

# ❌ 不要等到 40% 自动压缩（此时已有信息丢失风险）

# 每个 turn 的决策树
# ├── ✅ 成功 → 继续下一步
# ├── ❌ 失败 → /rewind（回退到上一个好状态）
# ├── 🔀 新话题 → /clear（开新对话）
# └── 📦 膨胀 → /compact（带保留关键上下文）

# Pro tip: 用状态栏实时监控上下文使用率
# 如果看到超过 30%，立即 compact
```

## 6. Worktree + Subagent 并行编程：多 Agent 同时改代码互不干扰
- **来源**: [ykdojo](https://github.com/ykdojo/claude-code-tips) on GitHub | ⭐ 9.4k stars
- **摘要**: 从 v2.1.198 起，subagent 默认在后台运行，并且支持 worktree 隔离。通过在 agent 的 frontmatter 中添加 `isolation: worktree`，每个 subagent 会在独立的 git worktree 中工作，彻底避免多个 agent 同时修改文件造成冲突。后台 agent 完成后还能自动提交、推送并创建 draft PR。配合自定义 agent 的 name、color、tool set 和 permission mode，可以构建一个完整的"AI 开发团队"。
- **代码示例**:
```markdown
<!-- .claude/agents/feature-builder.md -->
---
name: Feature Builder
model: opus
isolation: worktree
color: green
allowed_tools:
  - Read
  - Write
  - Edit
  - Bash
  - Grep
  - Glob
permission_mode: bypassPermissions
---

Build the requested feature following TDD:
1. Write failing tests first
2. Implement until tests pass
3. Refactor for clarity
4. Commit and push to a feature branch

<!-- .claude/agents/code-reviewer.md -->
---
name: Code Reviewer
model: opus
isolation: worktree
color: blue
allowed_tools:
  - Read
  - Grep
  - Glob
---

Review the specified PR for:
- Logic errors and edge cases
- Security vulnerabilities
- Performance implications
- Test coverage gaps
```

## 7. cc-copilot-bridge：用 GitHub Copilot Pro+ 路由 Claude Code 调用，成本降低 99%
- **来源**: [FlorianBruniaux](https://github.com/FlorianBruniaux/claude-code-ultimate-guide) on GitHub | ⭐ 5.5k stars
- **摘要**: 社区开发的 `cc-copilot-bridge` 工具可以将 Claude Code 的 API 调用通过 GitHub Copilot Pro+ 订阅进行路由，从而将 token 成本降低高达 99%。对于已有 Copilot Pro+ 订阅的开发者来说，这意味着可以近乎免费地使用 Claude Code。该工具来自 claude-code-ultimate-guide 仓库，同时该仓库还提供了 38 个安全 hook（包括危险操作拦截、prompt 注入检测、Unicode 注入扫描、密钥扫描）和系统化的 MCP 服务器信任验证框架。
- **代码示例**:
```bash
# cc-copilot-bridge 设置步骤
# 前提：需要 GitHub Copilot Pro+ 订阅

# 1. 安装 bridge
npm install -g cc-copilot-bridge

# 2. 配置环境变量
export CC_COPILOT_BRIDGE=true
export GITHUB_TOKEN=your_copilot_token

# 3. 启动 Claude Code（调用自动路由）
claude

# 成本对比：
# 直接 API 调用：~$50-200/月（重度使用）
# 通过 Copilot Pro+ 路由：~$19/月（固定订阅费）
# 节省：高达 99%

# 注意：适合个人开发者和小团队
# 企业用户建议使用官方 Max 订阅
```

## 8. 路径作用域 Rules：按文件路径懒加载规则，CLAUDE.md 永远不超载
- **来源**: [abhishekray07](https://github.com/abhishekray07/claude-md-templates) on GitHub | ⭐ 294 stars
- **摘要**: 将规则从臃肿的 CLAUDE.md 拆分到 `.claude/rules/` 目录下的独立文件中，并通过 YAML frontmatter 的 glob 模式指定每个规则的适用路径。当 Claude 操作 `src/api/` 下的文件时，只有 API 相关的规则会被加载；操作测试文件时，只有测试规则生效。这解决了"CLAUDE.md 超过 80 行后 Claude 开始忽略部分内容"的核心痛点。结合子目录级 CLAUDE.md（如 `src/auth/CLAUDE.md`），可以构建一个精确到模块的渐进式知识披露体系。
- **代码示例**:
```markdown
<!-- .claude/rules/api-design.md -->
---
path: src/api/**
---
## API Conventions
- RESTful naming: plural nouns for resources
- Always return { data, error, meta } envelope
- Use Zod for request validation
- Rate limit all public endpoints

<!-- .claude/rules/testing.md -->
---
path: "**/*.test.ts"
---
## Test Standards
- Minimum 80% branch coverage for new code
- Use factories, not fixtures
- No network calls in unit tests
- Name pattern: should_expectedBehavior_when_condition

<!-- 目录结构 -->
.claude/
├── CLAUDE.md              # 核心规则（<60 行）
├── rules/
│   ├── api-design.md      # 仅 src/api/** 时加载
│   ├── testing.md         # 仅 *.test.ts 时加载
│   ├── code-style.md      # 通用代码风格
│   └── security.md        # 安全相关规则
src/
├── auth/CLAUDE.md         # auth 模块专属上下文
└── api/CLAUDE.md          # API 模块专属上下文
```
