## 1. CLAUDE.md 保持精简，控制在 150 行以内
- **来源**: [shanraisshan/claude-code-best-practice](https://github.com/shanraisshan/claude-code-best-practice) on GitHub | 🔥 热门最佳实践仓库
- **摘要**: 社区实测发现 CLAUDE.md 超过约 150 行后，Claude 对指令的遵循度会明显下降。建议将核心规则精简到 150 行以内，把领域知识和详细说明迁移到 Skills 文件中。用 `.claude/rules` 配合路径前缀实现按目录加载规则，只在 Claude 操作相关文件时才注入对应指令，避免全局规则膨胀。
- **代码示例**:
```markdown
# CLAUDE.md（保持精简）
## 技术栈
- Next.js 15 + TypeScript + Tailwind

## 关键命令
- 测试: npm test
- Lint: npm run lint

## 核心规则
- 修改前先跑相关测试
- 不要编辑 generated/ 目录下的文件
- 未经确认不得修改依赖
```

## 2. Esc+Esc 回退检查点：放心让 Claude 大胆尝试
- **来源**: [Santiago (@svpino)](https://x.com/svpino/status/2050563493708112190) on X | 🔥 高互动技巧合集（数千转发）
- **摘要**: Santiago 分享的 20 条 Claude Code 技巧中，Esc+Esc 回退到任意历史检查点被认为是最实用的功能之一。有了这个"免费撤销"，你可以让 Claude 放心尝试高风险的重构或实验性修改——不满意就一键回退，代码恢复到之前的状态。这彻底改变了与 AI 编程的工作心态：从小心翼翼变成大胆探索。
- **代码示例**:
```bash
# 让 Claude 尝试一个激进的重构
> 把这个类重构成函数式风格，用 hooks 替代所有生命周期方法

# 如果结果不理想
Esc+Esc   # 弹出检查点列表，选择回退点
          # 代码自动恢复，无需手动 git stash/reset

# 其他实用快捷键
Ctrl+V    # 直接粘贴截图给 Claude 分析
Ctrl+G    # 打开编辑器撰写长提示词
```

## 3. 目录级 CLAUDE.md 覆盖：为不同模块定制规则
- **来源**: [luongnv89/claude-howto](https://github.com/luongnv89/claude-howto) on GitHub | 🔥 实用模板指南仓库
- **摘要**: CLAUDE.md 支持多层级配置——项目根目录放全局规则，子目录放模块专属规则。例如 `/api` 目录下的 CLAUDE.md 可以强调 REST 规范和错误处理，`/components` 目录下的则侧重组件设计模式。Claude 操作某个目录的文件时，会自动加载该目录及其父目录的所有 CLAUDE.md，实现精确的上下文控制。
- **代码示例**:
```
项目结构:
├── CLAUDE.md              # 全局规则：技术栈、代码风格
├── api/
│   └── CLAUDE.md          # API 专属：RESTful 规范、错误码
├── components/
│   └── CLAUDE.md          # 组件专属：Props 类型、测试要求
└── ~/.claude/CLAUDE.md    # 个人配置：偏好的代码风格
```

## 5. 自动格式化 Hook 的隐患：隐藏 Claude 的结构性错误
- **来源**: [mvanhorn](https://x.com/mvanhorn/article/2035857346602340637) on X | 🔥 热门技巧文章
- **摘要**: 有开发者在"Every Claude Code Hack I Know"中提醒：如果你设置了 pre-commit hook 自动运行 Prettier/ESLint fix，要注意它可能掩盖 Claude 犯的结构性错误。自动格式化会让代码看起来整洁，但底层逻辑问题依然存在。建议在 hook 中只做格式检查（不自动修复），让 Claude 自己看到并理解错误信息后修正，这样它能从错误中学习，后续生成的代码质量更高。
- **代码示例**:
```json
// .claude/settings.json - hooks 配置建议
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "command": "npx eslint --no-fix $CLAUDE_FILE_PATH",
      "blocking": true
    }]
  }
}
// 用 --no-fix 让 Claude 看到错误并自行修正
// 而非 --fix 自动修复后掩盖问题
```

## 6. CLAUDE.md 用错误驱动更新，定期修剪
- **来源**: [centminmod/my-claude-code-setup](https://github.com/centminmod/my-claude-code-setup) on GitHub | 🔥 热门配置模板仓库
- **摘要**: 与其一开始就写一份完美的 CLAUDE.md，不如采用"错误驱动"的维护策略：每当 Claude 犯错（比如修改了不该动的文件、忽略了编码规范），就让它把新规则追加到 CLAUDE.md 中。这样规则库是从真实问题中生长出来的，每条规则都有存在的理由。但别忘了定期修剪——当规则超过上限时，合并相似项、删除过时项，保持文件精干有效。
- **代码示例**:
```bash
# 当 Claude 犯错时
> 你刚才不应该修改 generated/ 目录，请把这条规则加到 CLAUDE.md

# Claude 会自动追加规则到 CLAUDE.md:
# "永远不要修改 generated/ 目录下的任何文件"

# 定期维护（建议每季度一次）
> 审查 CLAUDE.md，合并重复规则，删除不再适用的条目，
> 确保总行数在 150 行以内
```

## 8. 敏感信息隔离：用 .local 文件管理个人配置
- **来源**: [CanArslanDev/claude-code-setup](https://github.com/CanArslanDev/claude-code-setup) on GitHub | 🔥 一键配置指南仓库
- **摘要**: 团队协作中最常见的安全隐患之一是把 API 密钥、本地路径等敏感信息写进了会被 git 追踪的文件。正确做法是使用 `CLAUDE.local.md` 和 `settings.local.json` 存放个人配置——这些文件默认被 .gitignore 忽略，不会提交到仓库。把所有涉及个人环境的内容（本地数据库地址、测试 API key、个人偏好设置）都放在 .local 文件中。
- **代码示例**:
```markdown
# CLAUDE.local.md（不会被 git 追踪）
## 本地环境
- 数据库地址: localhost:5432
- 测试 API Key: sk-test-xxx
- 偏好: 使用 Vim 键位绑定

# .gitignore 中确保包含:
CLAUDE.local.md
.claude/settings.local.json
```
